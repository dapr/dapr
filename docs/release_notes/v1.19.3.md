# Dapr 1.19.3

This update contains the following bug fixes and improvements:
- [Redis pub/sub leaked connections when subscriptions restarted](#redis-pubsub-leaked-connections-when-subscriptions-restarted)
- [Anthropic conversation component rejected assistant turns that only call tools](#anthropic-conversation-component-rejected-assistant-turns-that-only-call-tools)

## Redis pub/sub leaked connections when subscriptions restarted

### Problem

With `readTimeout` unset, the Redis pub/sub component sent `XREADGROUP` with `BLOCK 0` (wait forever) instead of using the documented 3s default.

### Impact

On Redis 7 and later, each time the sidecar stopped and restarted subscriptions, for example when the app's health check failed and recovered, readers on topics with no new messages kept their connections. After enough restarts the connection pool was full, and subscribing and publishing on that component failed with `redis: connection pool timeout` until the sidecar was restarted. Redis versions below 7 were not affected.

### Root Cause

The component passed `readTimeout` as the `XREADGROUP` block time, so an unset value meant no limit. The go-redis client used for Redis 7 and later does not interrupt a blocked read when its subscription is cancelled, so the read kept its connection until a message arrived on that topic.

### Solution

Redis pub/sub now defaults `readTimeout` to 3s, so `XREADGROUP` returns at least every 3 seconds and a stopped subscription gives its connection back. Blocking reads now wait for the block time plus `readTimeout` before timing out, so idle topics no longer log `i/o timeout`. Components that set `readTimeout` explicitly keep their value.

## Anthropic conversation component rejected assistant turns that only call tools

### Problem

A Conversation API request to a `conversation.anthropic` component failed when its history held an assistant message with tool calls and empty text.
The request returned `failed to create message: API returned unexpected status code: 400: messages: text content blocks must be non-empty`.

### Impact

You were affected if you use the Anthropic conversation component with tool calling and your client sends an assistant turn that only calls tools as an empty text part followed by the calls.
Dapr Agents does this, so an agent failed on the request that followed its first tool call.
The same requests succeeded on the OpenAI conversation component.

### Root Cause

Anthropic does not accept a text block with no text.
The component sent every part of an assistant message to Anthropic as it received it, including an empty text part.

### Solution

The Anthropic conversation component now leaves empty text parts out of assistant messages, and leaves out an assistant message that has no other part.
