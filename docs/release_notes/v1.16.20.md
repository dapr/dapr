# Dapr 1.16.20

This update contains the following bug fixes:
- [Daprd never reconnecting to Placement after a failed actor deactivation](#daprd-never-reconnecting-to-placement-after-a-failed-actor-deactivation)
- [Actor calls hanging forever after a slow Placement dissemination round](#actor-calls-hanging-forever-after-a-slow-placement-dissemination-round)
- [Pluggable pub/sub components delivered messages to the application one at a time](#pluggable-pubsub-components-delivered-messages-to-the-application-one-at-a-time)

## Daprd never reconnecting to Placement after a failed actor deactivation

### Problem

When a daprd sidecar lost its stream to the Placement service (for example after a Placement pod restart, a network disconnect, or a dissemination timeout), the sidecar could fail to reconnect and remained permanently disconnected until the pod was restarted.

The sidecar logged:

```
Error communicating with placement: EOF
Failed to reconnect to placement: error whilst deactivating all actors when shutting down client
```

and the metadata endpoint reported `placement: disconnected` and `hostReady: false`, while the Kubernetes readiness probe and the Scheduler connection remained healthy.

### Impact

You were affected on any Dapr 1.16.x version when a Placement stream disconnect coincided with an actor deactivation failure, for example the application returning a non-2xx status to the actor `DELETE` call while under load.

An affected sidecar never rejoined the placement table.
It kept routing actor invocations using its stale local table while the rest of the cluster placed those actors elsewhere, causing persistent `DaprBuiltInActorNotFoundRetries` warnings, hung or timed-out actor invocations across the namespace, and actor reminders on the affected host not firing.
The larger the replica count, the more likely a disconnect was to coincide with a failed deactivation.
The only recovery was restarting the affected pod, which Kubernetes never did on its own because the sidecar still reported healthy.

### Root Cause

Before reconnecting to Placement, the client halts all locally hosted actors so they can be reactivated in their new location.
A failure to deactivate any actor was treated as a fatal error for the reconnect, and the reconnect loop responded to that error by exiting the Placement client permanently instead of retrying.
Nothing restarted the client, and the rest of the runtime kept running without it.

### Solution

Halting actors during a Placement reconnect is now best effort: a failed deactivation is logged and the reconnect proceeds.
In addition, a failed reconnect attempt is now retried every second instead of terminating the Placement client, matching the recovery behavior of the other disconnect paths.

## Actor calls hanging forever after a slow Placement dissemination round

### Problem

After a Placement dissemination round in which the unlock order arrived more than 15 seconds after the lock order, a daprd sidecar could enter a state where every actor invocation and every actor state operation on that host hung until the caller timed out.
The sidecar looked healthy the whole time: the metadata endpoint reported `placement: connected`, `hostReady: true`, and actor runtime `RUNNING`, Kubernetes probes passed, and the sidecar kept logging `Placement tables updated` for new table versions.

Applications observed actor method calls timing out at their configured HTTP timeout, actor state operations from inside actor methods failing after the .NET HttpClient default of 100 seconds, and the sidecar logging errors such as:

```
error getting actor state: context canceled
error invoke actor method: context canceled
```

### Impact

You were affected on any Dapr 1.16.x version whenever a dissemination round overran the sidecar's 15 second unlock failsafe, which is most likely in large actor deployments where one slow host delays the round for everyone.
Once triggered, the affected sidecar failed effectively all actor calls for the actors it owned, while calls it made to actors on other hosts kept succeeding.
The condition never self-healed and was invisible to health checks; the only recovery was restarting the affected pod.

### Root Cause

The sidecar pairs Placement lock and unlock orders with two counters, and a 15 second failsafe force-unlocks the actor table when an unlock order is late.
When the failsafe fired, it advanced the unlock counter to catch up; when the late unlock order then arrived anyway, it advanced the counter a second time, leaving the two counters permanently out of step.
From then on every unlock order failed the pairing check and returned without releasing the table lock, and the failsafe never fired again because its condition also relied on the desynchronized counters.
The table stayed write locked forever, blocking every actor lookup and actor state operation on the host.

### Solution

The unlock handler now resynchronizes the counters when an unlock order arrives with no paired lock, such as after the failsafe already released the round, instead of letting the counters drift apart.
The failsafe no longer depends on the counters at all: it now releases the table lock whenever the same lock acquisition is still held after the timeout, so no counter state can prevent it from firing.
With both changes, the worst case for any malformed or delayed order sequence is a single 15 second stall instead of a permanently wedged host.

## Pluggable pub/sub components delivered messages to the application one at a time

### Problem

Messages received from a pluggable pub/sub component were dispatched to the application serially.
The receive loop blocked on the handler, which invokes the application, waits for its response and only then acknowledges, so the next message could not be received until the previous one was fully handled.
Each subscription was limited to a single message in flight and its ceiling became the inverse of the per-message latency.
Publishing was unaffected, so a subscriber fell steadily behind a publisher it had previously kept up with, and the queue grew without any error being logged.

Bulk subscribe degraded along with it.
The runtime assembles bulk batches out of concurrent handler calls, so with one caller at a time the configured `maxMessagesCount` could never be reached and every message became its own application request.

### Impact

You were affected if you consumed messages through a pluggable pub/sub component on v1.16.0 or later.
Measured against a RabbitMQ pluggable component publishing 300,000 messages at 5,000 msg/s, consumption fell from 5,004 to 3,026 msg/s, p95 end-to-end latency rose from 15 ms to 37,945 ms, and bulk batches collapsed from a mean of 10.1 messages to exactly 1.
The throughput ceiling tracks handler latency, so the slower the application handler, the more severe the effect: a handler taking 60 ms tops out near 16 msg/s regardless of broker or component capacity.
Built-in pub/sub components were not affected.

### Root Cause

The serialization was collateral damage of a change that set out to stop in-flight input binding events from being cancelled during graceful shutdown.
That change removed the `WaitGroup` `pullMessages` used to wait on in-flight handlers, by then redundant because the runtime tracks in-flight messages itself in `pkg/runtime/subscription`, and collapsed the dispatching goroutine along with it.
Input bindings kept their concurrent dispatch in that same change, and the `safeSend` mutex that exists to make concurrent dispatch safe was left in place here.

### Solution

Messages are dispatched concurrently again, following the shape input bindings already use, so more than one message can be in flight per subscription.
Sends on the stream remain serialized by the existing mutex.
In-flight handlers are now waited on before the stream is closed, so a handler that is still running when the subscription is torn down can still acknowledge the message it has already processed instead of leaving it to be redelivered.
Graceful shutdown semantics are unchanged: draining, pausing and the deadline live in `pkg/runtime/subscription` and count handlers rather than stream goroutines.
