# Dapr 1.16.20

This update contains the following bug fixes:
- [Daprd never reconnecting to Placement after a failed actor deactivation](#daprd-never-reconnecting-to-placement-after-a-failed-actor-deactivation)

## Daprd never reconnecting to Placement after a failed actor deactivation

### Problem

When a daprd sidecar lost its stream to the Placement service (for example after a Placement pod restart, a network disconnect, or a dissemination timeout), the sidecar could fail to reconnect and remained permanently disconnected until the pod was restarted.

The sidecar logged:

```
Error communicating with placement: EOF
Failed to reconnect to placement: error whilst deactivating all actors when shutting down client
```

and the metadata endpoint reported `placement: disconnected` and `hostReady: false`, while the Kubernetes readiness probe and the Scheduler connection remained healthy.

### Impact

You were affected on any Dapr 1.16.x version when a Placement stream disconnect coincided with an actor deactivation failure, for example the application returning a non-2xx status to the actor `DELETE` call while under load.

An affected sidecar never rejoined the placement table.
It kept routing actor invocations using its stale local table while the rest of the cluster placed those actors elsewhere, causing persistent `DaprBuiltInActorNotFoundRetries` warnings, hung or timed-out actor invocations across the namespace, and actor reminders on the affected host not firing.
The larger the replica count, the more likely a disconnect was to coincide with a failed deactivation.
The only recovery was restarting the affected pod, which Kubernetes never did on its own because the sidecar still reported healthy.

### Root Cause

Before reconnecting to Placement, the client halts all locally hosted actors so they can be reactivated in their new location.
A failure to deactivate any actor was treated as a fatal error for the reconnect, and the reconnect loop responded to that error by exiting the Placement client permanently instead of retrying.
Nothing restarted the client, and the rest of the runtime kept running without it.

### Solution

Halting actors during a Placement reconnect is now best effort: a failed deactivation is logged and the reconnect proceeds.
In addition, a failed reconnect attempt is now retried every second instead of terminating the Placement client, matching the recovery behavior of the other disconnect paths.
