## Sidecar crashed when a workflow executor actor was deactivated during a call

### Problem

The sidecar could panic and exit with:

```text
panic: sync: WaitGroup is reused before previous Wait has returned
```

It happened when an internal workflow executor actor, which delivers activity and workflow task results, was deactivated at the same moment a call for it arrived.

### Impact

You were affected if you ran workflows with a clustered workflow deployment. The sidecar restarted, and the workflows it hosted resumed after the restart.

### Root Cause

The executor actor counted its in-flight calls with a `WaitGroup` and waited on it during deactivation, while a new call could start counting from zero during that wait. Go does not allow this, and can panic when it happens.

### Solution

The executor actor refuses calls once its deactivation has started, and the caller retries them on a new executor actor.

## Data races in sidecar shutdown, actor and workflow deactivation, input bindings and pub/sub

### Problem

A sidecar built with the Go race detector reported data races in five places:

1. Shutting down while the sidecar was still starting its gRPC servers.
2. Deactivating an actor, for example because it was idle, while calls or reminders for it were arriving.
3. Deactivating a workflow instance while invocations for it were arriving.
4. Closing an input binding, for example on a hot reload, while it was delivering events.
5. Shutting down while the application's health changed, which stops pub/sub subscriptions.

### Impact

1. A gRPC server started after shutdown had begun was never closed, and kept its port bound. This matters when the sidecar restarts its runtime in-process, for example on a hot reload.
2. A call could be admitted to an actor after it had been deactivated.
3. A late invocation could run a turn on a workflow instance that had already been deactivated and removed.
4. Closing the binding could race with an incoming event.
5. Pending pub/sub subscription retries were cancelled from two goroutines at once.

In cases 2, 3 and 4 the Go runtime can also panic with `sync: WaitGroup misuse` or `WaitGroup is reused before previous Wait has returned`.

### Root Cause

1. The shutdown path read and closed the gRPC servers without synchronizing with the startup path that created and started them.
2. The actor's lock could admit a call after it was closed, and registered the call with a `WaitGroup` that the close was already waiting on. It also read the request's method after the HTTP actor transport had started rewriting it.
3. The workflow orchestrator registered invocations with a `WaitGroup` that deactivation could already be waiting on.
4. The input binding registered each event with a `WaitGroup` that the close could already be waiting on.
5. The pub/sub subscriber cancelled its retries on shutdown without the lock that the app health handler holds.

### Solution

1. Starting and closing the gRPC servers are serialized, and a server is not started once shutdown has begun.
2. A closed actor lock refuses new calls and registers calls only while it is open. It records the method once when the call arrives.
3. A workflow instance refuses invocations once deactivated, and the caller retries on a new instance.
4. Closing an input binding waits for events in flight, and refuses later events.
5. The subscriber cancels its retries under its lock on shutdown.

## An actor stopped accepting calls after a reentrant call exceeded maxStackDepth

### Problem

With actor reentrancy enabled, once a reentrant call was rejected for exceeding `maxStackDepth`, the actor stopped accepting calls. Every later call to it waited until its context timed out.

### Impact

You were affected if you use actor reentrancy with `maxStackDepth` set and a call chain exceeded it. The actor stayed unavailable until the sidecar restarted.

### Root Cause

The actor lock counted the rejected reentrant call in the call chain's depth and never removed it, so the chain never finished and the next call never started.

### Solution

The actor lock checks the depth limit before counting the call, so a rejected call no longer changes the depth.

## Sidecar kept activity executions pending after their workflows completed

### Problem

The sidecar held on to activity executions whose workflows had already completed, and released them only when it shut down. At shutdown it logged three lines for each of them:

```text
<instance>/<activity>#<task>: failed before receiving activity result
activity-processor: failed to process work item: context canceled
<instance>: aborting activity execution (::<task>)
```

### Impact

You were affected if you ran workflows without the clustered workflow deployment and reused workflow instance IDs, for example by purging an instance and scheduling it again under the same ID, while an activity of the previous run was still executing.

Each held execution kept its goroutines and memory until the sidecar restarted, so long-lived sidecars grew with every overlap. In stress tests a sidecar held about 90 of them, which was about 250 goroutines and 30 MB of memory. If `maxConcurrentActivityInvocations` is set, each held execution also kept one activity slot, which reduces the number of activities that can run at once.

Workflow results were not affected.

### Root Cause

The workflow engine tracks each pending activity execution by its workflow instance ID and task ID. A new run of a reused instance ID schedules the same task IDs as the previous run. When an execution of the previous run was still pending on the same sidecar, the new run's execution replaced it in the engine's tracking. The previous execution could then never receive its result or be cancelled, so it waited until the sidecar shut down.

### Solution

The sidecar now uses durabletask-go v0.12.6, which keeps every pending execution of a task, so each result and cancellation reaches all of them and none is left pending.
When executions of the same task overlap, a result cannot be matched to one of them, so they are aborted and re-run, and the application's SDK receives an error for that result.

## Data races in the sidecar's Scheduler, hot reload and actor placement connections

### Problem

A sidecar built with the Go race detector reported `WARNING: DATA RACE` in three places, with no fault injected:

```text
google.golang.org/grpc.(*clientStream).CloseSend()
github.com/dapr/dapr/pkg/runtime/scheduler/internal/cluster.(*streamer).outgoing.deferwrap1()   streamer.go:106
github.com/dapr/dapr/pkg/runtime/scheduler/internal/cluster.(*streamer).receive.func1()         streamer.go:62
```

1. The Scheduler job stream was closed by two goroutines at once each time the sidecar disconnected from a Scheduler, which happens on every reconnect.
2. The hot reload streams from the Operator, for Components, Subscriptions, Configurations, HTTPEndpoints, Resiliencies, MCPServers and WorkflowAccessPolicies, were closed at shutdown while they were being re-established.
3. The actor placement in-flight call tracking was updated concurrently by an actor call finishing and by the placement connection closing.

### Impact

You were affected if you ran actors, workflows, jobs or hot reloading, which covers most deployments.

The first two races were in shutdown and reconnect paths.
They left gRPC stream state unsynchronized and could drop job results that were still being sent when a Scheduler stream ended.
A sidecar shutting down could also wait for the Operator to end each hot reload stream, rather than stopping it.

The third race could break actor placement guarantees.
When the placement connection closed, which in v1.18 happens on every placement leader change, the sidecar waits for in-flight actor calls to drain before handing actors over.
An actor call that returned after the next placement session had started could release a different call's in-flight record, so the next drain did not wait for that call and the actor could briefly run on two hosts.

### Root Cause

1. Both the receive and send goroutines of the Scheduler stream closed its send side when they exited. gRPC does not allow `CloseSend` concurrently with itself or with `Send`.
2. The hot reload loader's shutdown closed the current Operator stream before waiting for its reconnect goroutine to exit, while that goroutine was replacing the stream. The first stream was also opened with the caller's context, so shutdown could not cancel it.
3. Each in-flight claim recorded whether it had been released in a plain boolean, written by both the call and the placement loop. The tracking lock and its event loop were also returned to a pool when the placement connection closed, so a late release from the previous session could be delivered to the next session's lock.

### Solution

1. Only the send goroutine closes the Scheduler stream, once and after its last send.
2. Hot reload shutdown cancels every Operator stream, including the first one. It waits for the reconnect goroutine to exit before closing the stream.
3. A claim is released at most once, guarded by an atomic flag. The in-flight lock and its event loop are no longer reused, so a late release from a closed placement session is dropped.
