# Dapr 1.18.7

This update contains the following bug fixes and improvements:
- [Sidecar crashed when a workflow executor actor was deactivated during a call](#sidecar-crashed-when-a-workflow-executor-actor-was-deactivated-during-a-call)
- [Sidecar kept activity executions pending after their workflows completed](#sidecar-kept-activity-executions-pending-after-their-workflows-completed)

## Sidecar crashed when a workflow executor actor was deactivated during a call

### Problem

The sidecar could panic and exit with:

```text
panic: sync: WaitGroup is reused before previous Wait has returned
```

It happened when an internal workflow executor actor, which delivers activity and workflow task results, was deactivated at the same moment a call for it arrived.

### Impact

You were affected if you ran workflows with a clustered workflow deployment. The sidecar restarted, and the workflows it hosted resumed after the restart.

### Root Cause

The executor actor counted its in-flight calls with a `WaitGroup` and waited on it during deactivation, while a new call could start counting from zero during that wait. Go does not allow this, and can panic when it happens.

### Solution

The executor actor refuses calls once its deactivation has started, and the caller retries them on a new executor actor.

## Sidecar kept activity executions pending after their workflows completed

### Problem

The sidecar held on to activity executions whose workflows had already completed, and released them only when it shut down. At shutdown it logged three lines for each of them:

```text
<instance>/<activity>#<task>: failed before receiving activity result
activity-processor: failed to process work item: context canceled
<instance>: aborting activity execution (::<task>)
```

### Impact

You were affected if you ran workflows without the clustered workflow deployment and reused workflow instance IDs, for example by purging an instance and scheduling it again under the same ID, while an activity of the previous run was still executing.

Each held execution kept its goroutines and memory until the sidecar restarted, so long-lived sidecars grew with every overlap. In stress tests a sidecar held about 90 of them, which was about 250 goroutines and 30 MB of memory. If `maxConcurrentActivityInvocations` is set, each held execution also kept one activity slot, which reduces the number of activities that can run at once.

Workflow results were not affected.

### Root Cause

The workflow engine tracks each pending activity execution by its workflow instance ID and task ID. A new run of a reused instance ID schedules the same task IDs as the previous run. When an execution of the previous run was still pending on the same sidecar, the new run's execution replaced it in the engine's tracking. The previous execution could then never receive its result or be cancelled, so it waited until the sidecar shut down.

### Solution

The sidecar now uses durabletask-go v0.12.6, which keeps every pending execution of a task, so each result and cancellation reaches all of them and none is left pending.
When executions of the same task overlap, a result cannot be matched to one of them, so they are aborted and re-run, and the application's SDK receives an error for that result.
