# Dapr 1.17.16

This update contains the following security fix:
- [Security: Service invocation delivered spoofed caller identity headers to the target app](#security-service-invocation-delivered-spoofed-caller-identity-headers-to-the-target-app)

## Security: Service invocation delivered spoofed caller identity headers to the target app

### Problem

On service invocation, Dapr tells the target app who called it through the `dapr-caller-app-id`, `dapr-caller-namespace` and `dapr-callee-app-id` headers (gRPC metadata for gRPC apps).
A calling app could send its own values for these headers, and they reached the target app alongside the values Dapr set:

```text
Dapr-Caller-App-Id: admin
Dapr-Caller-App-Id: checkout
```

- Service invocation through the HTTP API: a header such as `Dapr-Caller-App-Id: admin`, in any casing, reached the target app as a second value of the header, in random order.
- gRPC proxying: the calling app's `dapr-caller-app-id` value always came before the real one, and Dapr never set `dapr-caller-namespace`, so the target app received only the namespace the calling app sent.

### Impact

You were affected if a target app makes authorisation or tenancy decisions from these headers and uses the first value it finds (as Go's `http.Header.Get` and `metadata.Get(...)[0]` in gRPC do).
Any app able to invoke the target app could then make it believe the call came from a different app or namespace.

Dapr's own access control policies, workflow access policies and metrics were not affected: they use the calling sidecar's mTLS identity, not these headers.

### Root Cause

The HTTP API copies every request header into the invocation metadata and keeps the casing Go gives it, so `dapr-caller-app-id` sent by an app is stored as `Dapr-Caller-App-Id`.
The calling sidecar then set the identity headers under their lowercase names without removing other casings, so both keys travelled to the target sidecar, which merged them into one header with two values when delivering the request to the app.
Self-invocation already removed these headers in any casing, but cross-app invocation did not.

On the gRPC proxy path, the calling sidecar forwarded the app's metadata and appended its own identity values instead of replacing them, and never set `dapr-caller-namespace`.
The target sidecar passed all of these values to the app without checking them.

### Solution

- The calling sidecar now removes these headers in any casing before setting them, on every service invocation path.
- On the gRPC proxy path, the calling sidecar replaces the identity metadata instead of appending to it, and now also sets `dapr-caller-namespace`.
- The target sidecar now sets these headers itself before delivering the request, so apps are protected even while calling sidecars still run an older version. This covers service invocation and actor invocation received from another sidecar. With mTLS enabled, `dapr-caller-app-id` and `dapr-caller-namespace` come from the calling sidecar's mTLS certificate (SPIFFE ID) and, for service invocation, `dapr-callee-app-id` is the target's own app ID. With mTLS disabled, the target sidecar keeps the single value set by the calling sidecar and drops the rest.
- Caller identity headers in actor and workflow metadata received from the user-facing APIs are now removed in any casing.
- gRPC proxied self-invocation (an app invoking its own app ID) now carries the identity headers set by the sidecar, with caller and callee both the app itself, as HTTP self-invocation already did.

This is a behaviour change: with mTLS enabled, the caller identity headers an app receives are now always set by its own sidecar from the caller's mTLS identity, and gRPC proxied calls now carry `dapr-caller-namespace`.
With mTLS disabled there is no verified identity to fall back on: if the calling sidecar has not been upgraded, `dapr-caller-namespace` on gRPC proxied calls still reflects the value the calling app sent, so upgrade every sidecar to close the gap fully.
