# Dapr 1.19

We're excited to announce the release of Dapr 1.19!

The main changes in this release:

- **Faster workflows, jobs and reminders.** In the nightly performance tests against 1.18.0, workflow throughput is up to 40% higher. The p99 latency of actor reminder registration is 71% lower, and the p99 latency of Jobs scheduling is 33% lower. Workflow workers in the Python, Java, .NET and Go SDKs now get only the new events of each turn, not the full history.
- **Workflows across apps.** A workflow client can now start, get, raise events on, pause, resume, terminate, purge and rerun a [workflow that another app owns](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-multi-app/). [Access policies](https://v1-19.docs.dapr.io/operations/security/workflow-access-policy/) decide which app can do what. A new `requires` rule allows a schedule only when the caller's history contains the required upstream events. A workflow can also start a [detached workflow](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-detached/) that outlives it.
- **New building blocks (alpha).** [Binary Store](https://v1-19.docs.dapr.io/developing-applications/building-blocks/binarystore/) stores large files in Amazon S3 and S3-compatible stores, Azure Blob Storage, Azure Data Lake Storage, Google Cloud Storage and OCI Object Storage. [Search](https://v1-19.docs.dapr.io/developing-applications/building-blocks/search/) and [Vector](https://v1-19.docs.dapr.io/developing-applications/building-blocks/vector/) index and query documents and vectors, with Meilisearch components.
- **Dapr MCP server (alpha).** The [Dapr MCP server](https://v1-19.docs.dapr.io/developing-ai/mcp/dapr-mcp-server/) gives AI agents and IDE assistants the building blocks of a sidecar as Model Context Protocol tools. It ships as a separate binary, on its own release cycle.
- **Actors.** With [actor placement in the Scheduler](https://v1-19.docs.dapr.io/concepts/dapr-services/scheduler/) (opt-in), each reminder goes straight to the host that runs the actor. The cluster then does not need the Placement service. New APIs list and get actor [timers](https://v1-19.docs.dapr.io/developing-applications/building-blocks/actors/actors-timers-reminders/) over HTTP and gRPC, and list reminders over HTTP. When an actor moves to another host, the old host deletes its timers, so they no longer fire twice.
- **Kafka transactions.** [Kafka pub/sub](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-apache-kafka/) can make a bulk publish atomic, read only committed records, and run consume-transform-produce in one transaction. All three are opt-in.
- **Operations.** [Logs](https://v1-19.docs.dapr.io/operations/observability/logging/) can go to several destinations, with file rotation and a configurable timestamp format. Workload identity certificates carry the image references of the pod. Every Kubernetes Service that Dapr creates sets `appProtocol` for service meshes.
- **Security.** Four security fixes for service invocation, the Scheduler and workflows, which also shipped in 1.18.6. Three of them change behavior.

Read [Breaking Changes](#breaking-changes) and [Deprecation Notices](#deprecation-notices) before you upgrade. 1.19 contains behavior changes that can affect an upgrade, mostly in the SDKs.


Thanks to all the new and existing contributors who helped make this release happen.

If you're new to Dapr, visit the [getting started](https://docs.dapr.io/getting-started/) page and familiarize yourself with Dapr.

The docs have been updated with all the new features and changes of this release. To get started with new capabilities introduced in this release, go to the [Concepts](https://docs.dapr.io/concepts/) and the [Developing applications](https://docs.dapr.io/developing-applications/).

Go to the [upgrading Dapr](#upgrading-to-dapr-119) section for steps to upgrade to version 1.19.

## Highlights

These are the v1.19 release highlights:

### Faster workflows, jobs and reminders

Compared with the published v1.18.0 run, the nightly [performance](https://v1-19.docs.dapr.io/operations/performance-and-scalability/) tests on master show:

- Workflows: throughput is 40% higher in `TestWorkflowWithConstantVUs` and 32% higher in `TestSeriesWorkflowWithMaxVUs`.
- Jobs scheduling: p99 latency is 33% lower (39.5 ms to 26.3 ms), and the test now sustains the full requested 1000 QPS (921 QPS on 1.18.0).
- Actor reminder registration: p99 latency is 71% lower (148 ms to 43 ms), at 43% more registrations per second.
- Configuration subscribe: throughput is 67% higher over HTTP and about 2.8x over gRPC. This test varies up to 3x between runs, so treat the gRPC figure as indicative.

Service invocation, state and pub/sub publish show no change beyond run-to-run noise. The figures are medians of 8 runs from 23/09/2026 to 02/10/2026, on the same cluster as the v1.18.0 run.

Changes in this area include:

- Event-driven completion of work items.
- Cached tag maps for metrics on hot paths.
- Fewer state copies and event marshals per workflow turn.
- A separate size and payload-ratio aggregation for each meter.
- Large fan-outs: an empty-inbox wake-up reloads the workflow state only when its cache is stale, and a completed workflow no longer re-arms for duplicate late results. Before, each such wake-up re-read the whole history.

For workflows that run for minutes or hours, the `workflow` block of the metrics settings in `Configuration` now takes its own `latencyDistributionBuckets`, with a `latencyDistributionUnits` such as `1s`. The workflow and activity execution latency histograms then use buckets that fit those durations, instead of the shared millisecond buckets, where every long workflow landed in the top bucket. The repository also ships Grafana dashboards for workflows and for the Scheduler in [`grafana/`](https://github.com/dapr/dapr/tree/release-1.19/grafana): execution and activity rates, latency percentiles, failures, client operations and payload size against the limit, which no dashboard charted before. The etcd panels of the Scheduler dashboard need `--etcd-metrics=extensive`.

The 1.19 charts are published after the GA tag on the [performance results](https://v1-19.docs.dapr.io/operations/performance-and-scalability/perf-results/) page.

#### Workflow workers get only the new history

Long-running workflows now spend less time on each turn. Before 1.19, a workflow worker received the full history of an instance on every turn. For long-running instances, sending and parsing that history took most of the time of each turn.

A [worker](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-stateful-client/) can now advertise the `WORKER_CAPABILITY_STATEFUL_HISTORY` capability on its work-item stream. The worker then keeps the history of each instance in a cache. When the worker already has the history from an earlier turn on the same stream, the sidecar sends only the new events. The worker builds the full history from its cache and the new events, so the sidecar no longer re-sends, and the worker no longer re-parses, the whole history on every turn. On a reconnect the sidecar sends the full history. If the worker has evicted the instance from its cache, it fetches the full history from the sidecar. Either case adds latency, but it does not change the result.

On an idle work-item stream, the sidecar now sends a health ping every 30 seconds to a worker that advertises the `WORKER_CAPABILITY_HEALTH_PING` capability. Load balancers such as AWS ALB and nginx close an idle stream after 60 seconds, and before 1.19 that cost the worker a reconnect and a full history resend. The 1.19 Python, Java and .NET SDKs and durabletask-go v0.15 (Go SDK 1.16) advertise the capability. Set `DAPR_WORKFLOW_HEALTH_PING_INTERVAL` on daprd to change the interval.

The protocol is in [durabletask-go#110](https://github.com/dapr/durabletask-go/pull/110). The SDKs that support it turn it on by default:

| SDK | Stateful history |
|---|---|
| Python | On by default. To turn it off, set `disable_stateful_history=True` on `WorkflowRuntime`. |
| Java | On by default. To turn it off, call `WorkflowRuntimeBuilder.withStatefulHistoryDisabled(true)`. |
| .NET | On by default. To turn it off, set `WorkflowRuntimeOptions.DisableStatefulHistory`. |
| Go | On by default from go-sdk v1.16.0 (durabletask-go v0.15.0). The Go SDK has no switch to turn it off; `client.WithStatefulHistoryDisabled()` in durabletask-go does. |
| JavaScript | No. The new JavaScript workflow engine does not use the shared DurableTask client library. |

#### `WorkflowsFastPath` preview feature

The new [`WorkflowsFastPath`](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-fast-path/) [preview feature](https://v1-19.docs.dapr.io/operations/support/support-preview-features/) is off by default. With it, a workflow wake-up runs on the host that armed it, instead of through a scheduler reminder for each event. A repeating janitor reminder for each instance keeps the work durable.

The fast path stays off when a scheduler-enforced [workflow or activity concurrency limit](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-concurrency/) is configured, and daprd logs the reason. Fast-path drives run work items directly on the sidecar, so they would bypass the concurrency limit of the scheduler.

### Workflows across apps

A workflow client can now run its operations on a workflow that [another app in the same namespace](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-multi-app/) owns: start, get, raise event, pause, resume, terminate, purge and rerun. Listing instance IDs and reading history stay local. Use this when one app manages workflows that another app owns, for example an API or operations service that starts and inspects order workflows owned by the orders app, without registering those workflows itself. Before 1.19, a workflow could already start child workflows and activities in another app, but the client operations worked only on workflows of the calling app.

The `WorkflowAccessPolicy` of the target app decides which operations a caller can do, per operation and per workflow name. The workflow request protos have a new optional `app_id` field, and the HTTP endpoints accept an `appID` query parameter. Rerun is available through the SDK workflow clients only. The engine side is in [durabletask-go#117](https://github.com/dapr/durabletask-go/pull/117). When no workflow worker is connected for the target app, local or remote, these operations now fail at once with a clear error instead of a 20 second retry and an actor routing error (see Breaking Changes).

#### Workflow access policy `requires`, detached workflows, duplicate instance IDs and child retries

- A [`WorkflowAccessPolicy`](https://v1-19.docs.dapr.io/operations/security/workflow-access-policy/) rule can now have a `requires` block. The operation is then allowed only when the [propagated workflow history](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-history-propagation/) of the caller contains the listed events. A rule can require proof that the caller saw a specific upstream event, instead of allowing the caller unconditionally. For example, a billing app can allow its `charge` activity only for callers whose history holds an `event.raised` named `order.validated` from the orders app, so a caller cannot skip the validation step. `requires` is an ordered list of up to 20 entries, each with `appID`, `eventType` (`activity.started`, `activity.completed`, `workflow.started`, `workflow.completed` or `event.raised`) and `name`. It applies to scheduling only: activity rules, or workflow rules whose only operation is `schedule`.
- A workflow can now start a [detached workflow](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-detached/). A detached workflow is an independent instance, with no link to its parent and no result back to it. In durabletask-go, the method is `WorkflowContext.ScheduleNewDetachedWorkflow`. Use it when a workflow needs to start work that should outlive it, such as a clean-up or report job, without waiting for the result. Before 1.19, the workaround was a client call inside an activity.
- [Scheduling through an SDK workflow client](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/howto-manage-workflow/) fails with the gRPC `AlreadyExists` status code when the instance ID belongs to an active (not completed) instance (in the sidecar since 1.18.2). The error message does not change, so an SDK can detect the conflict without parsing the message, and a client can start a workflow with a fixed instance ID as an idempotent call and treat `AlreadyExists` as already running. A completed instance ID is reused by default; it also returns `AlreadyExists` when the client sets `WithEnforceUniqueInstanceID` or when the old instance's child workflows have not finished. The Dapr runtime workflow API (HTTP and gRPC `StartWorkflowBeta1`) keeps its error response.
- A child workflow that runs as a retry attempt now records the instance ID of the first attempt in the parent's history. Each retry of a child workflow is a separate instance with its own ID, so tooling that reads a parent's history can now group the attempts of one call without walking the retry timers between them.

### Placement served by the Scheduler (opt-in)

With this feature on, the [Scheduler](https://v1-19.docs.dapr.io/concepts/dapr-services/scheduler/) places actors itself, and it sends each actor reminder straight to the host that runs the actor. With the standalone [Placement service](https://v1-19.docs.dapr.io/concepts/dapr-services/placement/), a reminder goes to any instance of the app, and that instance forwards it to the owner. The cluster also no longer needs the Placement service. The feature is off by default. Applications and sidecars need no configuration change.

Before you turn it on, upgrade every sidecar to 1.19 or later. An older sidecar can use only the Placement service. Once no Placement service remains, its actor and workflow APIs stall until you upgrade its pod, and the Scheduler logs a warning. The older sidecar does not stop the Scheduler from serving the upgraded sidecars.

To turn it on, set this Helm value, and pass it on every later `helm upgrade`, because Helm resets values you do not pass:

```yaml
global:
 scheduler:
 placement:
 enabled: true # default: false
```

How it works:

- The Helm chart does not deploy the Placement StatefulSet, Service or RBAC. It starts the Schedulers with `--placement-enabled=true`. The chart does not render unless `global.scheduler.enabled`, `global.actors.enabled` and `global.actors.serviceName=placement` are set.
- While a Placement service is still deployed, it stays the placement authority and the Schedulers do not serve placement. When the Placement pods are gone, the Schedulers detect it and take over within a few seconds — but the Schedulers also restart to pick up the new flag as part of this same upgrade, so expect actor and workflow activity to pause for longer than that while the Schedulers come back up.
- You can turn the feature on or off without sidecar restarts. When you turn it off, the Placement service is redeployed and sidecars move back to it. Sidecars switch as soon as the Placement pod exists, so expect a short pause until it is ready.
- Actor state is not lost. The two services place actors differently, so actors are deactivated and reactivated on their new hosts once per switch, in either direction.
- The Scheduler needs `get`, `list` and `watch` on `pods` in the Dapr namespace to detect a Placement service. The chart adds this as the `dapr-scheduler-pods` Role. If you use custom RBAC, add it before any 1.19 upgrade.

To check which authority a sidecar uses, look for `Connected to scheduler placement leader <address>` in its log. The other authority logs `Connected to placement <address>`. In the Scheduler, `dapr_scheduler_placement_leader` and `dapr_scheduler_placement_streams_connected` show the leader and the connected sidecars, and `dapr_scheduler_placement_incapable_sidecars` counts sidecars older than 1.19.

New flags: daprd `--actors-placement-startup-timeout` (default 30s, annotation `dapr.io/actors-placement-startup-timeout`), and Scheduler `--placement-enabled`, `--placement-disseminate-timeout` (default 8s) and `--placement-disseminate-coalesce-window` (default 0). The two `--placement-disseminate-*` flags have no Helm value.

In self-hosted mode, use [`dapr init --scheduler-placement`](https://v1-19.docs.dapr.io/reference/cli/dapr-init/). It is not available with `-k` or `--slim`. It does not start the `dapr_placement` container, and it starts `dapr_scheduler` with `--placement-enabled=true`.

### Dapr MCP server (alpha)

The Dapr MCP server ([`dapr/dapr-mcp-server`](https://github.com/dapr/dapr-mcp-server)) is a standalone [Model Context Protocol](https://modelcontextprotocol.io/) server, written in Go, that runs next to a Dapr sidecar and turns its building blocks into MCP tools. Any MCP client can call them: Claude Desktop, Cursor, Claude Code, VS Code, [Dapr Agents](https://v1-19.docs.dapr.io/developing-ai/dapr-agents/), or your own agent.

The MCP server is a separate binary in its own repository, with its own version numbers and release cycle, and it is in alpha, so tool names, inputs and configuration can still change.

How it works:

- The server connects to the sidecar over gRPC with the usual settings, `DAPR_GRPC_PORT` and `DAPR_GRPC_ENDPOINT`. It retries five times, then exits.
- It reads the sidecar's metadata and registers tools for every building block that has at least one component loaded. `get_components`, `invoke_service` and `invoke_actor_method` are always registered.
- It serves MCP over stdio by default, for clients that launch it themselves, or over streamable HTTP with `--http`. Authentication, health endpoints and CORS apply to the HTTP transport only.
- Tools follow component hot reloading. Adding the first component of a type registers that type's tools, removing the last one takes them away, and connected clients are told that the list changed. A client that reads the tool list only once has to reconnect to see it.

The tools cover state including transactions, pub/sub, output bindings, secrets, service invocation, actors, distributed lock, cryptography and conversation. Each one carries the MCP safety annotations `readOnlyHint`, `destructiveHint` and `idempotentHint`.

Authentication is off until you set `AUTH_MODE`, which takes `oidc`, `spiffe`, `dapr-sentry` or `hybrid`. Turn it on whenever you serve over HTTP to anything other than localhost. The server can reach whatever its sidecar can reach, and it returns tool results to the model, including the values from `get_secret` and `get_bulk_secrets`, so scope its components and secrets to what the agent needs.

Telemetry is off until you set an OTLP endpoint. Over HTTP the server also serves `/livez`, `/startupz` and `/readyz` health endpoints.

### Actor timer and reminder APIs, timer ownership and activation ID

Actors get APIs to read their [timers and reminders](https://v1-19.docs.dapr.io/developing-applications/building-blocks/actors/actors-timers-reminders/):

- gRPC: [`ListActorTimers` and `GetActorTimer`](https://v1-19.docs.dapr.io/reference/api/actors_api/).
- HTTP: `GET /v1.0/actors/{actorType}/{actorId}/timers` and `GET /v1.0/actors/{actorType}/{actorId}/timers/{name}`.
- HTTP: `GET /v1.0/actors/{actorType}/{actorId}/reminders`, to match the gRPC `ListActorReminders` API.

Before 1.19, timers could not be read back at all, and reminders could be listed only over gRPC. Use the new APIs to check why a timer did not fire, or to build tooling that shows what an actor has scheduled.

When an actor moves to another host, its in-memory timers on the old host are now deleted. Before 1.19, the old host kept firing them, and the actor ran twice when the timer was registered again on the new host. A timer operation sent to a host that does not own the actor now fails with `ERR_ACTOR_TIMER_NOT_OWNED` (HTTP 403, gRPC `PermissionDenied`). A timer fire that was parked during a placement change, and whose timer the ownership sweep deleted, is dropped and counted in `timers_dropped_total`.

daprd now sends a `Dapr-Actor-Activation-Id` header on the invoke, reminder and timer callbacks to the app, and the same key as metadata on the gRPC actor callback stream. The ID is new each time daprd activates the actor, so an SDK can drop an actor object it kept from an earlier activation instead of reusing its cached state, for example after daprd deactivated the actor on its idle timeout and activated it again on the same host. No SDK uses the header in 1.19. The Go SDK change is [go-sdk#846](https://github.com/dapr/go-sdk/pull/846).

### Image references in workload SVIDs

Workload identity certificates now record which images run in the pod. A consumer can use this to link an mTLS identity or an attestation record to the exact image that ran. For example, it can find the workloads that run an image with a known CVE. On Kubernetes, [Sentry](https://v1-19.docs.dapr.io/concepts/dapr-services/sentry/) now adds the image references of the requesting pod's containers (the app containers and daprd) to the [workload identity certificate](https://v1-19.docs.dapr.io/operations/security/mtls/). Sentry stores them in a non-critical X.509 extension, as a list with one entry per container: the image as written in the pod spec and, when the container has already started, its digest. Sentry takes the image data from the pod object that the Kubernetes validator already reads, through its pod cache or the API server, not from the request. The pod cache now holds only pods with the `dapr.io/sidecar-injected` label.

### `appProtocol` on Kubernetes Services

Every [Kubernetes Service](https://v1-19.docs.dapr.io/operations/hosting/kubernetes/) that Dapr creates now sets `appProtocol` on each port. This includes the control-plane Services of the Helm chart and the sidecar Service that the operator creates for each app. A service mesh such as Istio can then select the protocol from this field instead of protocol sniffing. Ports that carry gRPC inside Dapr mTLS are declared `tls`, not `grpc`, so a mesh does not read the encrypted bytes as plain HTTP/2.

### Kafka pub/sub transactions

[Kafka pub/sub](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-apache-kafka/) gets transactions. Both modes are off by default:

- `producerTransactionsEnabled`: every publish, single or bulk, runs in a Kafka transaction on an idempotent producer. A bulk publish is then atomic: all entries commit or none do. The guarantee is atomicity per publish. There is no transaction recovery or fencing across component restarts. The mode needs `producerRequiredAcks: "all"`, `producerRetryMax` of 1 or more, and Kafka 0.11 or later. It lowers publish throughput.
- `consumerIsolationLevel: "read_committed"`: a subscription reads only committed records. It never sees records from open or aborted transactions.
- `consumerTransactionsEnabled`: each delivery runs inside a transaction (consume-transform-produce). The outputs of a delivery and its offset commit together, and failed attempts are invisible to `read_committed` consumers. Side effects outside Kafka, such as database writes, are not covered. The mode needs a consumer group, the same `producerRequiredAcks` and `producerRetryMax` settings, and Kafka 2.5 or later.

### Components

Pub/sub:

- **RabbitMQ: externally managed and consistent-hash exchanges.** Two new metadata options, [`exchangeDeclareMode` and `queueDeclareMode`](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-rabbitmq/), each `declare` (the default) or `passive`. In `passive` mode, the component expects the exchange or queue to already exist, instead of creating it. The component also accepts the `x-consistent-hash` exchange kind, for hash-based partitioning across queues.
- **Generic AMQP 1.0 pub/sub.** The [AMQP 1.0 component](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-amqp/) now also registers as `pubsub.amqp`. This form has no vendor-specific address prefix, so it works against any AMQP 1.0 broker. `pubsub.solace.amqp` keeps its original `topic://` and `queue://` prefixes. Existing Solace components keep working unchanged.
 - `anonymous` is now honored over `amqps://`, so a client certificate can be the only credential (mutual TLS without a username/password).
 - Publishing with `ttlInSeconds` no longer panics the sidecar, a lost connection reconnects with backoff, and a failed link no longer closes the shared connection.
 - Subscriptions can set `subscriptionName`, `durable`, `shared` and `selector`, so a named subscription can be durable, shared across replicas and filtered by the broker. New component settings: `containerID`, `durableMessages` and `applicationPropertiesFromMetadata`.

- **Kafka pub/sub and binding: connection timeouts and producer settings.** New metadata options [`dialTimeout`, `readTimeout` and `writeTimeout`](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-apache-kafka/) (30 seconds each), `metadataTimeout` (0, which is off), `producerRequiredAcks` (`all`, `local` or `none`; default `all`) and `producerRetryMax` (default 5). The defaults are the values the component used before, so an existing configuration does not change. The same options apply to the [Kafka binding](https://v1-19.docs.dapr.io/reference/components-reference/supported-bindings/kafka/).

Secret stores:

- **HashiCorp Vault: native Kubernetes auth.** Set [`vaultAuthMethod: kubernetes`](https://v1-19.docs.dapr.io/reference/components-reference/supported-secret-stores/hashicorp-vault/), and the component logs in to Vault with the pod's service account token. It no longer needs the Vault Agent Injector sidecar to get a token. `vaultAuthMethod: token` works as before.

Conversation:

- **Conversation API: `max_tokens`.** A [Conversation API](https://v1-19.docs.dapr.io/reference/api/conversation_api/) request can now cap how many tokens a call generates. Set `max_tokens` on the request, or `maxTokens` in the component metadata as a default. A request value greater than zero overrides the metadata default.
- **OpenAI conversation: opt-in Responses API.** Set `useResponsesAPI: "true"` in the [OpenAI component](https://v1-19.docs.dapr.io/reference/components-reference/supported-conversation/openai/) metadata, and the component calls `/v1/responses` instead of Chat Completions. Reasoning models that reject function tools on Chat Completions can then call tools. The setting is off by default, and it does not work with `apiType: azure`. [CONFIRM: Fabian]

### Structured logging: more output destinations and file rotation

The control-plane binaries and daprd take six new [logging](https://v1-19.docs.dapr.io/operations/observability/logging/) flags, from two `dapr/kit` changes:

- `--log-outputs`: a comma-separated list of log destinations (`stdout`, `stderr`, or a file path). It merges with `--log-file`, so an existing `--log-file` configuration is unchanged.
- `--log-file-max-size`, `--log-file-max-backups`, `--log-file-max-age` and `--log-file-compression`: rotation for file destinations. Without them, a file destination is a plain file that grows with no limit.
- `--log-timestamp-format`: a Go time layout for the log timestamp. The default, RFC3339 with nanoseconds, stays unless you set this flag.

All six flags default to off or empty, so a binary that sets none of them behaves as before. When rotation is on and no size is set, a file rotates at 100 MB. The sidecar injector has no annotation for these flags. See [log destinations and file rotation](https://v1-19.docs.dapr.io/operations/observability/logging/logs/#log-destinations-and-file-rotation).

## SDK Improvements

### Go SDK

The [Go SDK](https://v1-19.docs.dapr.io/developing-applications/sdks/) can now host actors over gRPC. The app receives actor invoke, reminder, timer and deactivate callbacks on one bidirectional stream (`SubscribeActorEventsAlpha1`), so it does not need an HTTP callback server. This uses the runtime feature from [dapr#9812](https://github.com/dapr/dapr/pull/9812) (1.18).

Workflows: the workflow client lists instances, reads the history of an instance and reruns a workflow from an event (`ListInstanceIDs`, `GetInstanceHistory`, `RerunWorkflowFromEvent`). A new example and a section in the client guide show how to use them.

Workflows: `WorkflowContext.Select` waits for the first of several tasks to complete and returns its index, the `WhenAny` that the other SDKs already had (in durabletask-go v0.15.0, which go-sdk 1.16 pins). Use it for an approval gate that waits for `Approve`, `Reject` or a timeout timer, whichever comes first. Before, the only way was to poll each event with short `WaitForSingleEvent` timeouts, and every poll added a timer and a history entry, so a workflow parked at a gate grew its history without bound. `Select` adds no timers or history entries, and the losing tasks stay pending to be awaited or selected later.

### .NET SDK
The v1.19 release of the [Dapr .NET SDK](https://docs.dapr.io/developing-applications/sdks/dotnet/) continues the move toward focused, building-block-specific packages. New clients include `Dapr.BinaryStore` for streaming binary uploads and downloads, alongside `Dapr.Search` and `Dapr.Vector` for the new alpha search and vector APIs. Each includes source generators for strongly typed clients.

This release introduces `Dapr.Actors.Next`, a new actor programming model alongside the existing Actors SDK, with generated proxies and registration, constructor injection, state schema migration, built-in state machines, and deterministic testing. In .NET 10 in-process benchmarks measuring client-side overhead (not end-to-end actor execution), proxy creation was approximately 38× faster and SDK-only invocation 10× faster, with 99% and 97% fewer allocated bytes, respectively, than the existing `Dapr.Actors` SDK.

The new `Dapr.Messaging` package provides Native AOT-compatible, strongly typed publish/subscribe support with generated message handlers. It supports streaming subscriptions, HTTP and gRPC push delivery, bulk messaging, content-based routing, and dead-letter topics.

Workflows gain opt-in large-payload offloading through Binary Store, detached workflow scheduling, and history caching with delta work items to reduce repeated transfers. In a benchmark available in the repository using a 2 MB document, explicit data references roughly halved total workflow completion time and reduced managed allocations by 66% compared with inline payloads, with history caching enabled. This release also improves workflow tracing, versioning, and connection reliability.

Finally, the Jobs client adds gRPC transport alongside HTTP, timezone-aware scheduling, and job listing and purging. New transactional outbox helpers simplify pairing state changes with published events, and the SDK adds .NET 11 preview support.

Do note that in the next v1.20 release, support for .NET 8 and 9 will be dropped as they will no longer be supported .NET frameworks as of November 2026.

## Upgrading to Dapr 1.19

To upgrade to this release of Dapr, follow the steps below to ensure a smooth upgrade.

### Local Machine / Self-hosted

Uninstall Dapr using the CLI you currently have installed. Note that this will remove the default `$HOME/.dapr` directory, binaries and all containers `dapr_redis`, `dapr_placement`, `dapr_scheduler` and `dapr_zipkin`, and the `dapr_scheduler` volume. Linux users need to run `sudo` if `docker` command needs sudo:

```bash
dapr uninstall --all
```

Download the latest release from [here](https://github.com/dapr/cli/releases) and put the `dapr` binary in your `PATH`.

Once you have installed the CLI, run:

```bash
dapr init --runtime-version=1.19.0
```

Use the full version, `1.19.0`. The CLI puts the version string into download URLs, so a short form such as `1.19` does not resolve. [`dapr init`](https://v1-19.docs.dapr.io/reference/cli/dapr-init/) without `--runtime-version` installs the newest GA runtime, never a release candidate.

Wait for the update to finish, then ensure you are using the latest version of Dapr (1.19.0) with:

```bash
$ dapr --version

CLI version: 1.19.0
Runtime version: 1.19.0
```

To serve actor placement from the Scheduler on a [self-hosted machine](https://v1-19.docs.dapr.io/operations/hosting/self-hosted/self-hosted-upgrade/), run `dapr init --scheduler-placement`. The flag is for self-hosted mode only and needs runtime 1.19 or later. It does not work with `-k` or with `--slim`. It does not start the `dapr_placement` container, and it starts the `dapr_scheduler` container with `--placement-enabled=true`. `dapr run` needs no change. See [Opt-in: Placement served by the Scheduler](#placement-served-by-the-scheduler-opt-in) for what changes in a cluster.

### Kubernetes

#### Upgrading from previous version

You can perform [zero-downtime upgrades](https://v1-19.docs.dapr.io/operations/hosting/kubernetes/kubernetes-upgrade/) using both Helm 3 and the Dapr CLI.

##### Upgrade using the CLI

Download the latest release from [here](https://github.com/dapr/cli/releases) and put the `dapr` binary in your `PATH`.

To upgrade Dapr, run:

```
dapr upgrade --runtime-version 1.19.0 -k
```

To upgrade with high availability mode, set the chart value. [`dapr upgrade`](https://v1-19.docs.dapr.io/reference/cli/dapr-upgrade/) has no `--enable-ha` flag; only `dapr init` has it:

```
dapr upgrade --runtime-version 1.19.0 -k --set global.ha.enabled=true
```

`dapr upgrade -k` also applies the updated CRDs, when you pass the full version.

Wait until the operation is finished and check your status with [`dapr status -k`](https://v1-19.docs.dapr.io/reference/cli/dapr-status/).

*Note: Make sure your deployments are restarted to pick the latest version of the Dapr sidecar.*

##### Upgrade using Helm

Dapr 1.19 updates two CRDs: `Configuration` (new workflow latency-bucket fields in the metrics settings) and `WorkflowAccessPolicy` (the new [`requires`](https://v1-19.docs.dapr.io/operations/security/workflow-access-policy/) field). `helm upgrade` does not update CRDs, so apply them first:

<!-- EDITOR: the raw.githubusercontent.com URLs below resolve only once the tag v1.19.0 exists. They return 404 until the GA tag is pushed. Check them after the tag. -->

```
kubectl apply -f https://raw.githubusercontent.com/dapr/dapr/v1.19.0/charts/dapr/crds/configuration.yaml
kubectl apply -f https://raw.githubusercontent.com/dapr/dapr/v1.19.0/charts/dapr/crds/workflowaccesspolicy.yaml
```

If you upgraded from 1.17 with Helm and did not apply the 1.18 CRDs, also apply `mcpservers.yaml` from the same location:

```
kubectl apply -f https://raw.githubusercontent.com/dapr/dapr/v1.19.0/charts/dapr/crds/mcpservers.yaml
```

Then upgrade the chart:

```
helm repo add dapr https://dapr.github.io/helm-charts/
helm repo update
```

##### Opt-in: Placement served by the Scheduler

The opt-in Helm value `global.scheduler.placement.enabled` (default `false`) makes the [Scheduler service](https://v1-19.docs.dapr.io/concepts/dapr-services/scheduler/) serve actor placement, instead of the standalone [Placement service](https://v1-19.docs.dapr.io/concepts/dapr-services/placement/). Follow these steps.

1. Prerequisites. Upgrade every sidecar to 1.19 or later first, and restart your applications after the control plane upgrade. If you use custom RBAC, make sure the Scheduler can get, list and watch `pods` in the Dapr namespace. Keep `global.scheduler.enabled`, `global.actors.enabled` and `global.actors.serviceName=placement` as they are. The chart fails to render without them.
2. Enable. Run `helm upgrade` with `--set global.scheduler.placement.enabled=true` and your usual values. Pass the value on every later `helm upgrade`, because Helm resets values you do not pass. With the CLI, `dapr upgrade -k --set global.scheduler.placement.enabled=true` passes the same value. The upgrade removes the Placement StatefulSet. The Schedulers detect this and take over within a few seconds — but the Schedulers also restart to pick up the new flag as part of this same upgrade, so expect actor and workflow activity to pause for longer than that while they come back up. No sidecar restarts are needed. Actors are re-placed once, and their state is kept.
3. Verify. Sidecars log `Connected to scheduler placement leader <address>`. Exactly one Scheduler reports `dapr_scheduler_placement_leader` = 1. If `dapr_scheduler_placement_incapable_sidecars` is above 0, or a Scheduler logs "A sidecar running an older Dapr version is connected", upgrade those pods. Their actor and workflow APIs stall.
4. Roll back. Upgrade with the value set to `false`. The Placement StatefulSet is redeployed, the Schedulers stop serving, and sidecars switch back to the Placement service without restarts. Actors are re-placed once more, and there is a short pause until the Placement pods are ready.

An older sidecar does not delay the switch. Once no Placement service remains, the Scheduler serves placement even if an older sidecar is still connected, and that sidecar's actor APIs stall until you upgrade its pod. It does not block placement for sidecars that have already upgraded. All Scheduler replicas must run with the same setting, which the chart ensures.

```yaml
global:
  scheduler:
    placement:
      enabled: true # default: false
```

## Downgrading to Earlier Versions

> [!warning] Do not roll back from 1.19 directly to 1.17.6 or earlier. The safe rollback target is 1.18.x.

Dapr 1.19 still issues the Ed25519 workload identity keys that Dapr 1.18 introduced (see the [1.18 release notes](https://github.com/dapr/dapr/blob/v1.18.0/docs/release_notes/v1.18.0.md)), and [Sentry](https://v1-19.docs.dapr.io/concepts/dapr-services/sentry/) persists the Ed25519-keyed CA into the `dapr-trust-bundle` secret. Versions of Sentry before **1.17.7** cannot parse this bundle and will crash on startup with:

```
fatal: error creating CA: failed to get CA bundle:
failed to verify CA bundle: unsupported key type ed25519.PrivateKey
```

When Sentry is down, no new [workload certificates](https://v1-19.docs.dapr.io/operations/security/mtls/) can be issued. Existing sidecars with unexpired certificates keep working, but any sidecar restart or certificate expiry will fail to obtain a new identity. Dapr 1.19 does not change this floor from 1.18.

### Compatibility matrix

| From | To | Result |
|---|---|---|
| 1.19 | 1.18.x | Safe. 1.18 and 1.19 write the same trust bundle format. |
| 1.19 | **1.17.7+** | Safe. 1.17.7 backports the Ed25519 PEM-decoder fix ([#9904](https://github.com/dapr/dapr/pull/9904)) so Sentry can read the trust bundle as-is. |
| 1.19 | 1.17.6 or earlier | Sentry crash-loops at startup. Do **not** attempt this rollback. |
| 1.17.6 or earlier | 1.19 | Safe. Sentry accepts CSRs of any algorithm, and existing ECDSA P-256 bundles are read transparently, as in 1.18. |

### Safe rollback path

If you must downgrade below 1.17.7, **go through 1.17.7 first**:

1. Roll the control plane back to **1.17.7**. It includes the Ed25519 parsing fix and is the earliest version that can read a trust bundle written by 1.18 or 1.19.
2. Allow Sentry to stabilise and confirm `dapr status -k` is healthy.
3. From 1.17.7, downgrade to your target version. You may want to rotate the CA first to an algorithm the target version generates natively. See your Sentry CA rotation runbook.

### Rolling back the control plane

Use Helm rollback (preferred) or re-install at the target version:

```bash
# Helm: list revisions, then roll back to the desired one
helm history dapr -n dapr-system
helm rollback dapr <REVISION> -n dapr-system --wait

# Or pin a specific version
helm upgrade dapr dapr/dapr --version 1.18.7 --namespace dapr-system --wait
```

After the control plane is back, perform a rolling restart of your application Deployments so sidecars pick up the older injector image and re-issue their identities against the rolled-back Sentry.

### If you turned on Placement served by the Scheduler

If you turned on `global.scheduler.placement.enabled`, turn it off before you downgrade. Keep this order:

1. Set the value to `false` with `helm upgrade` and wait for the Placement pods to be ready. Sidecars then use the redeployed Placement service, with no restarts.
2. Verify that your sidecars reconnect to the Placement service. They log `Connected to placement <address>`.
3. Downgrade the control plane.
4. Downgrade the sidecars, with a rolling restart of your applications.

Turning the value off first is safe and sufficient. A 1.18 sidecar that starts while no Placement service is deployed has no placement, and its actor and workflow APIs stall. A `helm rollback` to a revision from before you turned the value on restores the Placement StatefulSet in the same operation.

### If you created `WorkflowAccessPolicy` rules that use `requires`

A 1.18 control plane and sidecar do not know that field and apply those rules without the gate. Remove or narrow those rules before you downgrade.

### What does NOT need to be rotated

Going **1.19 to 1.18.x or to 1.17.7** does not require manual CA rotation. The Ed25519-keyed bundle remains valid. 1.17.7 reads it, continues to issue *new* CSRs against the existing trust anchor, and ECDSA/RSA CSRs from 1.17.x sidecars are signed normally. Only re-rotate the CA if your downgrade target is below 1.17.7 or if your security posture requires it.

## Breaking Changes

> [!warning] Review carefully before upgrading

The changes below can require action when you upgrade from 1.18 to 1.19. The Dapr runtime API changes in 1.19 are additive. Most items here are behavior changes or SDK changes.

### Dapr runtime and Kubernetes

- **Helm upgrades: apply the 1.19 CRDs first.** `helm upgrade` does not update CRDs. Until the 1.19 `WorkflowAccessPolicy` CRD is applied, the API server drops the new [`requires`](https://v1-19.docs.dapr.io/operations/security/workflow-access-policy/) field, so a rule written with `requires` applies without that gate. See [Upgrading to Dapr 1.19](#upgrading-to-dapr-119).
- **Scheduler RBAC gets read access to pods in the Dapr namespace.** The chart adds a `dapr-scheduler-pods` Role and RoleBinding in the Dapr namespace that give the Scheduler `get`, `list` and `watch` on `pods`. The Scheduler watches the Placement pods in its own namespace to detect whether a Placement service is deployed. It needs this whether or not you turn on Placement served by the Scheduler. The `dapr-scheduler` ClusterRole (or Role, in namespaced RBAC mode) keeps `namespaces` only. The Helm chart applies this on upgrade. If you manage RBAC outside the chart, or run policy checks against minimal RBAC scopes, account for the new Role. [#10873](https://github.com/dapr/dapr/pull/10873)
- **Dapr Kubernetes Services set `appProtocol`.** Every port of every [Service](https://v1-19.docs.dapr.io/operations/hosting/kubernetes/) that Dapr creates now declares `appProtocol` (`http`, `grpc`, `tls`, `https` or `tcp`). A service mesh that selects proxy behavior from this field can now treat these ports differently. Ports that carry gRPC inside Dapr mTLS are declared `tls`. [#10232](https://github.com/dapr/dapr/pull/10232)
- **Workflow: no `output` for a failed workflow.** The [workflow Get API](https://v1-19.docs.dapr.io/reference/api/workflow_api/) no longer copies the failure message into `dapr.workflow.output` for a workflow in the `FAILED` state. Read `dapr.workflow.failure.error_message` and `dapr.workflow.failure.error_type` instead. [#10138](https://github.com/dapr/dapr/pull/10138)
- **Scheduler retries instead of exiting.** When the Scheduler server stops with a runtime error, for example because its embedded store is briefly unavailable, the Scheduler now recreates it in the process. It uses a jittered backoff, from 500 ms up to 10 s. Meanwhile, its healthz endpoint reports not ready. For these errors, it no longer exits and restarts. Alerts that count Scheduler pod restarts no longer see this condition. Use readiness or the logs instead. A port that the Scheduler cannot bind is the exception, see the next entry. [#10345](https://github.com/dapr/dapr/pull/10345)
- **Scheduler exits when it cannot bind its port.** The retry in the previous entry does not apply to a bind failure. The Scheduler process exits, and Kubernetes restarts it, as in 1.18, so alerts that count Scheduler pod restarts still see this condition. The Scheduler port, 50006, is in the default Linux ephemeral port range, so one of the process's own outbound connections can hold it. daprd now binds its internal gRPC port (default 50002) once, before it connects to Sentry, the operator and the Schedulers, and keeps it across SIGHUP reloads. [#10817](https://github.com/dapr/dapr/pull/10817), [#10820](https://github.com/dapr/dapr/pull/10820)
- **Scheduler keeps 10,000 etcd revisions, not 1,000,000.** The default retention drops from `1000000` to `10000`, both for the flag `--etcd-compaction-retention` and for the Helm value `dapr_scheduler.etcdCompactionRetention`. The compaction mode stays `revision`. Every revision of a deleted job keeps the job's payload until it is compacted, so the old default kept the payloads of the last million writes. After 15 hours of chaos testing, that was 2.7 GB of database and 3.4 GB of Scheduler memory, for 19 MB of live jobs. On the 1Gi volume that clusters installed before 1.17.7 keep, the database filled the disk and etcd writes failed. The database now holds at most 10,000 revisions plus 5 minutes of writes. The retention bounds the number of revisions, not their size. A value that you set yourself is not changed, and `helm upgrade --reuse-values` keeps the old `1000000`, so pass the new value or drop the override. A Scheduler watch that falls more than 10,000 revisions behind, for example during a leadership change under a write burst, is cancelled by etcd. The Scheduler then re-reads the job list and reconnects, and job API calls wait until it is ready. [#10818](https://github.com/dapr/dapr/pull/10818)
- **Metrics endpoints answer only GET and HEAD.** The [metrics server](https://v1-19.docs.dapr.io/operations/observability/metrics/) answered every HTTP method with 200 and the metrics text. It now answers POST, PUT, PATCH and DELETE with 405 and `Allow: GET, HEAD`. Prometheus scrapes with GET, so scraping is unchanged. Update scripts or probes that call the endpoint with another method. [#10669](https://github.com/dapr/dapr/pull/10669)
- **Jobs and reminders: a timezone with `@every` is rejected.** A [schedule](https://v1-19.docs.dapr.io/developing-applications/building-blocks/jobs/jobs-features-concepts/) such as `CRON_TZ=Europe/Rome @every 1h` now fails at parse time with `timezone is not supported for @every schedules`. Before, the timezone was silently ignored, because an `@every` schedule fires at a fixed interval and has no wall clock. Remove the prefix from `@every` schedules. Cron expressions with a timezone keep working. The same change is in 1.18.3. [kit#161](https://github.com/dapr/kit/pull/161)
- **Actor timers: only the owning host accepts timer operations.** A [timer operation](https://v1-19.docs.dapr.io/developing-applications/building-blocks/actors/actors-timers-reminders/) now fails on a sidecar that does not own the actor. The error is `ERR_ACTOR_TIMER_NOT_OWNED` (HTTP 403, gRPC `PermissionDenied`). In 1.18 the same call succeeded and could leak a timer. This can surface during actor rebalancing. [#10380](https://github.com/dapr/dapr/pull/10380)
- **Bounded actor reminder and timer span names.** The reminder and timer HTTP endpoints, including the new list and get endpoints, now emit span names in the form `<API name>/<actorType>`, for example `RegisterActorReminder/OrderActor` or `ListActorTimers/OrderActor`. The span name no longer contains the actor ID or the reminder or timer name. Update dashboards and alerts that match the old span names. [#10141](https://github.com/dapr/dapr/pull/10141)
- **`--healthz-listen-address` and `--metrics-listen-address` are honored.** Placement, Scheduler, Sentry, the sidecar injector and the operator now bind their healthz server to the address in `--healthz-listen-address`, and Sentry, the injector and the operator bind their metrics server to the address in `--metrics-listen-address`. Before 1.19 the flags had no effect, and the servers always bound all interfaces. The defaults are unchanged. Set the flag to a specific address to avoid a conflict on the healthz port with another process or interface. [#10394](https://github.com/dapr/dapr/pull/10394), [#10783](https://github.com/dapr/dapr/pull/10783)
- **Service invocation: caller identity headers come from the sidecar.** With mTLS on, the target app gets `dapr-caller-app-id` and `dapr-caller-namespace` only from its own sidecar. The sidecar sets them from the caller's mTLS identity, and it removes any value that the calling app sets. Calls through the gRPC proxy now also carry `dapr-caller-namespace`. The same change is in 1.18.6. [#10683](https://github.com/dapr/dapr/pull/10683)
- **Service invocation: some encoded methods fail.** A method with `%2F`, `%5C`, `%2E` (any letter case) or a literal `\` now fails before the access control check. This covers the HTTP and gRPC APIs, calls between sidecars, proxied gRPC calls and actor method invocation. The same change is in 1.18.6. [#10684](https://github.com/dapr/dapr/pull/10684)
- **Actor invoke API rejects reserved actor types.** gRPC `InvokeActor` and HTTP `/v1.0/actors/{type}/{id}/method/{method}` now reject every `dapr.internal.*` actor type. The error is `ERR_ACTOR_TYPE_RESERVED` (gRPC `PermissionDenied`, HTTP 403). The [actor state, reminder and timer APIs](https://v1-19.docs.dapr.io/reference/api/actors_api/) already did this. The same change is in 1.18.6. [#10685](https://github.com/dapr/dapr/pull/10685)
- **Workflow: a clear error when no workflow worker is connected.** Workflow actor types exist only while an app worker holds its work-item stream open. Without a connected worker, workflow operations now fail with `no workflow worker is connected for app '<app-id>'` instead of actor routing errors such as `did not find address for actor`. This covers start, raise event, terminate, pause, resume, purge, rerun and the wait operations, local and cross-app. Starting a workflow no longer retries in that case, so the error comes about 20 seconds sooner. The original error stays wrapped, so existing error codes still match. [#10865](https://github.com/dapr/dapr/pull/10865)
- **Pub/sub: deliveries without trace context start a root span.** When a message carries no W3C trace context (no `traceparent` and no legacy `traceid`), the sidecar now starts a new root span for the delivery, and the app receives a `traceparent` header. Before 1.19 such deliveries had no span and an empty `traceparent`, so a message published outside Dapr, or re-queued from a dead letter topic, was invisible in traces. Expect new traces for these messages. Nothing changes when tracing is off in the Configuration. [#10511](https://github.com/dapr/dapr/pull/10511)


### Components

- **Azure Event Hubs pub/sub and input binding: checkpoints move only past successfully handled events.** Before, the checkpoint could move past a failed batch. Now the component retries a failed batch with the `backOff*` settings until the handler succeeds. `backOffMaxRetries` no longer stops the retries, so an event that always fails holds the checkpoint of its partition. In the concurrent mode (`enableInOrderMessageDelivery: false`), the new [`maxConcurrentHandlers`](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-azure-eventhubs/) option (default `100`) limits the batches per partition that wait for a checkpoint. At that limit, the component pauses receives for the partition. A consumer group with no stored checkpoint now starts from the earliest retained event, not the latest. The same change is in 1.18.5 ([components-contrib#4606](https://github.com/dapr/components-contrib/pull/4606)). [components-contrib#4598](https://github.com/dapr/components-contrib/pull/4598)
- **Redis pub/sub: `redeliverInterval` is honored.** A duration string such as `"30s"` was ignored, and the [component](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-redis-pubsub/) always used 15 seconds. The configured value now applies. Components that do not set this field are not affected. [components-contrib#4601](https://github.com/dapr/components-contrib/pull/4601)
- **Solace AMQP pub/sub: a handler error redelivers the message.** `pubsub.solace.amqp` now answers a handler error with the AMQP `modified` outcome, so the broker delivers the message again. Before 1.19 it answered `rejected`, and the broker dead-lettered the message. TLS settings (`caCert`, `clientCert`, `clientKey`) on a plain `amqp://` URL are now rejected when the component initializes. Before, the component ignored them and connected without TLS. [components-contrib#4602](https://github.com/dapr/components-contrib/pull/4602)
- **Azure App Configuration: `retryDelay` is honored.** The [setting](https://v1-19.docs.dapr.io/reference/components-reference/supported-configuration-stores/azure-appconfig-configuration-store/) now controls the initial retry delay as documented. Before 1.19 the component used `maxRetryDelay` instead, so expect faster first retries. [components-contrib#4461](https://github.com/dapr/components-contrib/pull/4461)
- **Pub/sub: inbound retries stop when the component cancels the handler.** Inbound retries now use the handler's own context. Before 1.19, they used a context that never ended. A Kafka rebalance, for example, now stops the retries and the in-flight app call. The consumer that takes the partition then gets the message again. [Azure Service Bus](https://v1-19.docs.dapr.io/reference/components-reference/supported-pubsub/setup-azure-servicebus-topics/) (`handlerTimeoutInSec`, default 60 s) and Redis Streams (`processingTimeout`, default 60 s) put a timeout on the handler. That timeout now also limits these retries. A message that exceeds it goes to the [dead-letter topic](https://v1-19.docs.dapr.io/developing-applications/building-blocks/pubsub/pubsub-deadletter/), as on the bulk path. The same change is in 1.18.5. [#10497](https://github.com/dapr/dapr/pull/10497)
- **Anthropic conversation: new default model.** The [default model](https://v1-19.docs.dapr.io/reference/components-reference/supported-conversation/anthropic/) is now `claude-sonnet-4-6`, because the previous default model is retired. To keep a specific model, set `model` in the component metadata. [components-contrib#4532](https://github.com/dapr/components-contrib/pull/4532)

### Python SDK

- **Extension packages are no longer published separately.** Remove these packages from your project: `dapr-ext-fastapi`, `dapr-ext-grpc`, `dapr-ext-langgraph`, `dapr-ext-strands`, `dapr-ext-workflow` and `flask-dapr`. Then install the matching extras of the core package, for example `pip install "dapr[fastapi,workflow]"`. Uninstall the old packages before you reinstall `dapr`. [python-sdk#1054](https://github.com/dapr/python-sdk/pull/1054)
- **Higher minimum `protobuf` and `grpcio` versions.** The SDK needs `protobuf` 6.33.5 or later and `grpcio` and `grpcio-status` 1.81.1 or later. [python-sdk#1126](https://github.com/dapr/python-sdk/pull/1126)
- **`when_all` waits for every task.** A failing `when_all` now reports the first failure only after all tasks finish. [python-sdk#1166](https://github.com/dapr/python-sdk/pull/1166)
- **Streaming subscriptions no longer return `None` after a reconnect.** After a transient stream error, `next_message()` and iteration reconnect and return the next message. After five failed reconnects in one call they raise `StreamReconnectError`. A stream that the server ends cleanly now also reconnects instead of raising an error, and the async client also retries `INTERNAL` errors. If your code treated `None` as a reconnect signal, handle `StreamReconnectError` instead. [python-sdk#1231](https://github.com/dapr/python-sdk/pull/1231)
- **Workflow worker readiness reflects the connection.** `is_worker_ready()` and `wait_for_worker_ready()` now report not ready while the worker's work-item stream to the sidecar is down. Before 1.19 they stayed true after the first connection. Readiness probes built on these methods can now report not ready during a reconnect. [python-sdk#1312](https://github.com/dapr/python-sdk/pull/1312)
- **Actor `get_state_names` during a transaction.** The method now excludes only keys marked for removal. Earlier releases also returned removed keys and skipped updated ones. [python-sdk#1208](https://github.com/dapr/python-sdk/pull/1208)
- **Bulk publish metadata reaches plain entries.** `publish_metadata` on `publish_events` now applies to entries that do not carry their own metadata. Before 1.19 it was dropped for those entries. [python-sdk#1228](https://github.com/dapr/python-sdk/pull/1228)
- **`DAPR_API_TIMEOUT_SECONDS` no longer limits workflow waits.** `wait_for_workflow_start` and `wait_for_workflow_completion` ignore this setting. Without their own `timeout_in_seconds`, they wait with no time limit. If you relied on the global setting, pass `timeout_in_seconds`. [python-sdk#1244](https://github.com/dapr/python-sdk/pull/1244)
- **Conversation tool calls: `None` is rejected for required parameters.** When the SDK runs a tool function for a [Conversation API](https://v1-19.docs.dapr.io/reference/api/conversation_api/) tool call, `None` for a required (non-Optional) parameter was turned into the string `'None'`, or passed through and failed later with an unclear error. It now raises `ToolArgumentError`. Handle this error where you run tool calls. [python-sdk#1225](https://github.com/dapr/python-sdk/pull/1225)
- **Sub-second durations are serialized correctly.** `dapr.serializers.util.convert_to_dapr_duration` rounded a sub-second part of 0.5 seconds or more up into an extra second, so `timedelta(milliseconds=1500)` was sent as 2.5 seconds. It now sends 1.5 seconds. Actor reminders and timers with sub-second due times or periods now fire at the intended times. [python-sdk#1192](https://github.com/dapr/python-sdk/pull/1192)
- **Empty duration strings are rejected.** `dapr.serializers.util.convert_from_dapr_duration` parsed an empty string, or a string with no duration part, to a zero `timedelta`. It now raises `ValueError`. The actor gRPC client uses this helper for the `interval` of a retry policy, for example. [python-sdk#1221](https://github.com/dapr/python-sdk/pull/1221)
- **Relative unix socket endpoints fail fast.** A `unix://` endpoint with an authority, such as `unix://dapr.sock`, now raises `ValueError` when the client is created. Before 1.19 it waited until the connection timed out. gRPC needs an absolute path, as in `unix:///tmp/dapr.sock`. [python-sdk#1226](https://github.com/dapr/python-sdk/pull/1226)

### Java SDK

- **Spring integration requires Spring Boot 4.0.** Move to Spring Boot 4.0 before you take SDK 1.19. Or stay on SDK 1.18.x with Spring Boot 3.5. The two combinations are not binary compatible and fail at runtime. [java-sdk#1772](https://github.com/dapr/java-sdk/pull/1772)
- **Separate Spring Boot 4 artifacts are removed.** Replace `dapr-spring-boot-4-starter`, `dapr-spring-boot-4-starter-test` and `dapr-spring-boot-4-autoconfigure` with the artifacts without `-4` in the name. Replace `dapr-spring-6-data` with `dapr-spring-data`, and change imports from `io.dapr.spring6.data` to `io.dapr.spring.data`. [java-sdk#1772](https://github.com/dapr/java-sdk/pull/1772)
- **`WorkflowInstanceAlreadyExistsException`.** `scheduleNewWorkflow` throws this exception for a duplicate active instance ID instead of a raw `StatusRuntimeException`. [java-sdk#1782](https://github.com/dapr/java-sdk/pull/1782)
- **Netty 4.2.** The SDK now pulls Netty 4.2.x. A project that pins Netty 4.1.x directly can get a dependency conflict. [java-sdk#1814](https://github.com/dapr/java-sdk/pull/1814)

### .NET SDK

- **`DaprWorkflowClient.GetWorkflowStateAsync` rethrows errors other than NotFound.** Before SDK 1.18.5, any gRPC error from the runtime was swallowed into a `WorkflowState` with `Exists` set to `false`, so a transient error such as `Unavailable` looked like a workflow that does not exist. Now only a `NotFound` status gives `Exists == false`. Every other gRPC failure reaches your code as an `RpcException`. Handle `RpcException` where you poll workflow state. The same change is in 1.18.5. [dotnet-sdk#1877](https://github.com/dapr/dotnet-sdk/pull/1877)

### Workflow history cache in the Python, Java, .NET and Go SDKs

Workflow workers built with the 1.19 Python, Java or .NET SDK, or with Go SDK 1.16 (durabletask-go v0.15.0 or later), keep each workflow's [history in memory between turns](https://v1-19.docs.dapr.io/developing-applications/building-blocks/workflow/workflow-stateful-client/). This cache is on by default. If worker memory is limited, disable it with `disable_stateful_history` (Python), `withStatefulHistoryDisabled` (Java) or `DisableStatefulHistory` (.NET). The Go SDK has no switch; build the durabletask-go client with `client.WithStatefulHistoryDisabled()`. [python-sdk#1112](https://github.com/dapr/python-sdk/pull/1112), [java-sdk#1777](https://github.com/dapr/java-sdk/pull/1777), [dotnet-sdk#1862](https://github.com/dapr/dotnet-sdk/pull/1862)

### JavaScript SDK

- **New workflow engine.** The SDK replaced its workflow engine and wire-protocol handling. `WorkflowContext`, `DaprWorkflowClient` and `WorkflowState` keep their public method names, but re-test workflow code after you upgrade. [js-sdk#857](https://github.com/dapr/js-sdk/pull/857)
- **`grpcOptions` on `DaprWorkflowClient`.** Only message-size options still take effect. Keepalive, credential, compression and other grpc-js settings are ignored without an error. [js-sdk#857](https://github.com/dapr/js-sdk/pull/857)

### Dapr CLI

- **Workflow activity job names end in `::0`.** On a 1.19 runtime, [`dapr scheduler list`, `get` and `delete`](https://v1-19.docs.dapr.io/reference/cli/dapr-scheduler/) show workflow activity jobs as `activity/<app-id>/<instance-id>::<task-id>::0`. Earlier runtimes used the instance's generation in the last component, for example `::1` on the first run. Update scripts that build these names. [dapr#10283](https://github.com/dapr/dapr/pull/10283), [dapr#10504](https://github.com/dapr/dapr/pull/10504)


## Deprecation Notices

- **Standalone Placement service.** Starting with 1.19, the Scheduler can serve actor placement, enabled with `global.scheduler.placement.enabled=true` (`false` by default). The standalone Placement service remains the default in 1.19. The proposal is to make Scheduler-served placement the default in a later release, and to deprecate the standalone Placement service two releases after that. No removal date is set. No action is required in 1.19. See the [Placement service](https://docs.dapr.io/concepts/dapr-services/placement/) docs and [breaking changes and deprecations](https://docs.dapr.io/operations/support/breaking-changes-and-deprecations/).
- **Python SDK: CloudEvents handler type in `dapr.ext.grpc`.** Annotate the event parameter of topic handlers with `dapr.ext.grpc.SubscriptionMessage`, the same type that streaming subscriptions deliver. Handlers that are unannotated, or annotated with `cloudevents.sdk.event.v1.Event`, receive the CloudEvents-based event, and `subscribe()` emits a `DeprecationWarning` when it registers them. The timeline:
  - In 1.20, unannotated handlers receive `SubscriptionMessage`. The CloudEvents type is delivered only to handlers annotated with it.
  - In 1.21, `cloudevents` is no longer installed by the `dapr[grpc]` extra.
  - In 1.22, the CloudEvents-based type is removed.
  
  [python-sdk#1118](https://github.com/dapr/python-sdk/pull/1118)
- **Python SDK: `flask_dapr` import path and legacy extension installs.** The top-level `flask_dapr` package is now a shim that emits a `FutureWarning`. Import from `dapr.ext.flask` instead. `import dapr` also emits a `FutureWarning`, with the command to fix it, when it finds an old `dapr-ext-*` or `flask-dapr` package installed. Both warnings and the `flask_dapr` shim remain through 1.21 and are removed in 1.22. See [Breaking Changes](#breaking-changes). [python-sdk#1054](https://github.com/dapr/python-sdk/pull/1054)
- **Python SDK: `reuse_id_policy` on `schedule_new_workflow`.** Deprecated since 1.18.3. The parameter has no effect and emits a `DeprecationWarning`: an instance ID can always be reused once the existing instance is in a terminal state. Remove the argument. It is planned for removal in 1.21. [python-sdk#1145](https://github.com/dapr/python-sdk/pull/1145)
- **Python SDK: `http://` and `https://` prefixes on the gRPC endpoint.** A gRPC endpoint with a legacy scheme, for example `https://grpc.example.com:443` in `DAPR_GRPC_ENDPOINT`, now emits a `DeprecationWarning` that names the equivalent form, here `grpc.example.com:443?tls=true`. Use `host:port?tls=true` or `host:port?tls=false` instead. Before 1.19 the SDK emitted a `UserWarning`, so a warnings filter on `UserWarning` no longer matches. Python hides a `DeprecationWarning` in many cases, so run with `-W default` to see it. Endpoint parsing and TLS behavior are unchanged, and the endpoints keep working. No removal date is set. [python-sdk#1276](https://github.com/dapr/python-sdk/pull/1276)
- **.NET SDK: `Dapr.Actors` is in maintenance mode.** `Dapr.Actors` now receives security fixes only, and new actor development happens in `Dapr.Actors.Next`. `Dapr.Actors` is not deprecated: existing code keeps working, and no deprecation or removal date is set.
