# Dapr 1.19

We're excited to announce the release of Dapr 1.19!

The main changes in this release:

- The Scheduler can serve actor placement instead of the standalone Placement service. The feature is opt-in, and you can turn it on or off without sidecar restarts.
- A workflow worker that keeps a history cache now receives only the new events of each turn, not the full history.
- All workflow client operations can now target a workflow in another app. Before 1.19, only scheduling could.
- Actors get APIs to list and get timers and reminders, over HTTP and gRPC. When an actor moves to another host, its in-memory timers on the old host stop.
- The Jobs API accepts a timezone for schedules, and the actor state store supports hot reload like other components.
- Sentry adds the container image reference to workload identity certificates.
- On Kubernetes, every Service that Dapr creates sets `appProtocol`, and the control-plane binaries apply `--healthz-listen-address`.
- Four security fixes for service invocation, the Scheduler and workflows. Three of them change behavior, so read [Breaking Changes](#breaking-changes) before you upgrade.

Thanks to all the new and existing contributors who helped make this release happen.

If you're new to Dapr, visit the [getting started](https://docs.dapr.io/getting-started/) page and familiarize yourself with Dapr.

The docs have been updated with all the new features and changes of this release. To get started with new capabilities introduced in this release, go to the [Concepts](https://docs.dapr.io/concepts/) and the [Developing applications](https://docs.dapr.io/developing-applications/).

Go to the [upgrading Dapr](#upgrading-to-dapr-119) section for steps to upgrade to version 1.19.

> **Note:** 1.19 contains behavior changes that can affect an upgrade, mostly in the SDKs. Read [Breaking Changes](#breaking-changes) and [Deprecation Notices](#deprecation-notices) before you upgrade.

## Highlights

These are the v1.19 release highlights:

### Placement served by the Scheduler (opt-in)

The Scheduler service can now serve actor placement, so a cluster does not need the standalone Placement service. The feature is off by default. To turn it on, set this Helm value:

```yaml
global:
  scheduler:
    placement:
      enabled: true # default: false
```

How it works:

- When you turn it on, the Helm chart does not deploy the Placement StatefulSet.
- Sidecars take placement from the service that the control plane advertises. Applications need no change.
- The schedulers do not serve placement while a Placement service is still deployed, or while a sidecar older than 1.19 is connected. This keeps one placement authority during the rollout.
- You can turn the feature on or off without sidecar restarts. When you turn it off, sidecars go back to the redeployed Placement service. No actor state is lost.

Turn it on only when every sidecar in the cluster runs 1.19 or later. An older sidecar can use only the Placement service, so its actor and workflow APIs stop until you upgrade its pod.

Pull requests: [#10437](https://github.com/dapr/dapr/pull/10437), [#10438](https://github.com/dapr/dapr/pull/10438), [#10439](https://github.com/dapr/dapr/pull/10439), [#10364](https://github.com/dapr/dapr/pull/10364), [#10440](https://github.com/dapr/dapr/pull/10440), [#10416](https://github.com/dapr/dapr/pull/10416), [#10570](https://github.com/dapr/dapr/pull/10570).

### Stateful workflow worker stream (history deltas)

Before 1.19, a workflow worker received the full history of an instance on every turn. For long-running instances, sending and parsing that history took most of the time of each turn.

A worker can now advertise the `WORKER_CAPABILITY_STATEFUL_HISTORY` capability on its work-item stream. The worker then keeps the history of each instance in a cache. When the worker already has the history from an earlier turn on the same stream, the sidecar sends only the new events. The worker builds the full history from its cache and the new events. On a cache miss, for example after a reconnect or an eviction, the worker requests the full history. A miss adds latency, but it does not change the result.

The protocol is in [durabletask-go#110](https://github.com/dapr/durabletask-go/pull/110). The SDKs that support it turn it on by default:

| SDK | Stateful history |
|---|---|
| Python | On by default. To turn it off, set `disable_stateful_history=True` on `WorkflowRuntime` ([python-sdk#1112](https://github.com/dapr/python-sdk/pull/1112)). |
| Java | On by default. To turn it off, call `WorkflowRuntimeBuilder.withStatefulHistoryDisabled(true)` ([java-sdk#1777](https://github.com/dapr/java-sdk/pull/1777)). |
| .NET | On by default. To turn it off, set `WorkflowRuntimeOptions.DisableStatefulHistory` ([dotnet-sdk#1862](https://github.com/dapr/dotnet-sdk/pull/1862), [#1917](https://github.com/dapr/dotnet-sdk/pull/1917)). |
| Go | Not yet. The Go SDK gets it when it updates its durabletask-go dependency. |
| JavaScript | No. The new JavaScript workflow engine ([js-sdk#857](https://github.com/dapr/js-sdk/pull/857)) does not use the shared DurableTask client library. |

### Workflow and runtime performance

The daily performance tests on master show these changes between early July 2026 (9 runs) and 23 September to 2 October 2026 (8 runs):

- Jobs scheduling: p99 latency is 72% lower, and the test reaches its target of 1000 QPS.
- Actor reminder registration: p99 latency is 65% lower.
- Configuration subscribe: throughput is 31% to 38% higher.
- Workflows: throughput is 12% higher in two workflow tests (`TestWorkflowWithConstantVUs` and `TestSeriesWorkflowWithMaxVUs`).

Service invocation, state and pub/sub publish show no change beyond run-to-run noise.

Changes in this area include:

- Event-driven completion of work items ([#10379](https://github.com/dapr/dapr/pull/10379)).
- Cached tag maps for metrics on hot paths ([#10365](https://github.com/dapr/dapr/pull/10365)).
- Fewer state copies and event marshals per workflow turn ([#10366](https://github.com/dapr/dapr/pull/10366)).
- A separate size and payload-ratio aggregation for each meter ([#10591](https://github.com/dapr/dapr/pull/10591)).

### WorkflowsFastPath preview feature

The new `WorkflowsFastPath` preview feature ([#10368](https://github.com/dapr/dapr/pull/10368)) is off by default. With it, a workflow wake-up runs on the host that armed it, instead of through a scheduler reminder for each event. A repeating janitor reminder for each instance keeps the work durable.

The fast path stays off when a scheduler-enforced workflow or activity concurrency limit is configured, and daprd logs the reason ([#10406](https://github.com/dapr/dapr/pull/10406)). Fast-path drives run work items directly on the sidecar, so they would bypass the concurrency limit of the scheduler.

### Workflow operations across applications

Before 1.19, a workflow could start child workflows, activities and detached workflows in another app. The client operations worked only on workflows of the calling app. Now every client operation can target a workflow that another app in the same namespace owns ([#10293](https://github.com/dapr/dapr/pull/10293)). This covers start, get, raise event, pause, resume, terminate, purge and rerun.

The `WorkflowAccessPolicy` of the target app decides which operations a caller can do, per operation and per workflow name. The workflow request protos have a new optional `app_id` field, and the HTTP endpoints accept an `appID` query parameter. The engine side is in [durabletask-go#117](https://github.com/dapr/durabletask-go/pull/117).

### Workflow access policy `requires`, detached workflows and duplicate instance IDs

- A `WorkflowAccessPolicy` rule can now have a `requires` block ([#9884](https://github.com/dapr/dapr/pull/9884)). The operation is then allowed only when the propagated workflow history of the caller contains the listed events. A rule can require proof that the caller saw a specific upstream event, instead of allowing the caller unconditionally.
- A workflow can now start a detached workflow ([#9902](https://github.com/dapr/dapr/pull/9902), [durabletask-go#100](https://github.com/dapr/durabletask-go/pull/100)). A detached workflow is an independent instance, with no link to its parent and no result back to it. In durabletask-go, the method is `WorkflowContext.ScheduleNewDetachedWorkflow`. Before 1.19, the workaround was a client call inside an activity.
- Scheduling through an SDK workflow client now fails with the gRPC `AlreadyExists` status code when the instance ID belongs to a running instance ([#10153](https://github.com/dapr/dapr/pull/10153)). The error message does not change, so an SDK can detect the conflict without parsing the message. The HTTP workflow API keeps its error response.

### Actor timer and reminder APIs, and timer ownership

Actors get APIs to read their timers and reminders ([#10461](https://github.com/dapr/dapr/pull/10461), [#10487](https://github.com/dapr/dapr/pull/10487)):

- gRPC: `ListActorTimers` and `GetActorTimer`.
- HTTP: `GET /v1.0/actors/{actorType}/{actorId}/timers` and `GET /v1.0/actors/{actorType}/{actorId}/timers/{name}`.
- HTTP: `GET /v1.0/actors/{actorType}/{actorId}/reminders`, to match the gRPC `ListActorReminders` API.

When an actor moves to another host, its in-memory timers on the old host are now deleted ([#10380](https://github.com/dapr/dapr/pull/10380)). Before 1.19, the old host kept firing them, and the actor ran twice when the timer was registered again on the new host. A timer operation sent to a host that does not own the actor now fails with `ERR_ACTOR_TIMER_NOT_OWNED` (HTTP 403, gRPC `PermissionDenied`).

### Image references in workload SVIDs

Sentry now adds the container image reference of the requesting pod to the workload identity certificate ([#10282](https://github.com/dapr/dapr/pull/10282)). Sentry stores it in a non-critical X.509 extension. The reference has the image tag and, when Sentry can resolve it, the digest. A consumer can use it to link an mTLS identity or an attestation record to the exact image that ran. For example, it can find the workloads that run an image with a known CVE. Sentry takes the image data from the pod object that the Kubernetes validator already reads from the API server, not from the request.

### `appProtocol` on Kubernetes Services

Every Kubernetes Service that Dapr creates now sets `appProtocol` on each port ([#10232](https://github.com/dapr/dapr/pull/10232)). This includes the control-plane Services of the Helm chart and the sidecar Service that the operator creates for each app. A service mesh such as Istio can then select the protocol from this field instead of protocol sniffing. Ports that carry gRPC inside Dapr mTLS are declared `tls`, not `grpc`, so a mesh does not read the encrypted bytes as plain HTTP/2.

### `--healthz-listen-address` now takes effect

The control-plane binaries (placement, scheduler, sentry, injector and operator) have a `--healthz-listen-address` flag, but the shared healthz server ignored it and always bound all interfaces. The flag now takes effect ([#10394](https://github.com/dapr/dapr/pull/10394)). This also fixes start-up failures on hosts where a wildcard bind on the healthz port conflicts with another process or interface.

### Kafka pub/sub transactions

Kafka pub/sub gets transactions ([components-contrib#4508](https://github.com/dapr/components-contrib/pull/4508)):

- Transactional publishing puts every publish, single or bulk, in a Kafka transaction on an idempotent producer. A bulk publish is then atomic.
- With `consumerIsolationLevel: "read_committed"`, a subscription reads only committed records. It never sees records from open or aborted transactions.
- An opt-in mode runs each delivery inside a transaction, for exactly-once consume-transform-produce within Kafka.

### Components

- **RabbitMQ pub/sub: externally managed and consistent-hash exchanges.** Two new metadata options, `exchangeDeclareMode` and `queueDeclareMode`, each `declare` (the default) or `passive`. In `passive` mode, the component expects the exchange or queue to already exist, instead of creating it. The component also accepts the `x-consistent-hash` exchange kind, for hash-based partitioning across queues ([components-contrib#4552](https://github.com/dapr/components-contrib/pull/4552)).
- **Conversation API: `max_tokens`.** A Conversation API request can now cap how many tokens a call generates. Without a cap, a runaway generation can run for minutes. Set `max_tokens` on the request, or `maxTokens` in the component metadata as a default ([#10322](https://github.com/dapr/dapr/pull/10322), [components-contrib#4501](https://github.com/dapr/components-contrib/pull/4501)).
- **SQL Server output binding.** A new `bindings.sqlserver` output binding runs your own SQL statements and stored procedures against Microsoft SQL Server or Azure SQL. The existing `state.sqlserver` component stays a key-value state store with its own fixed schema. Use the new binding against a database that has its own tables and procedures ([components-contrib#4485](https://github.com/dapr/components-contrib/pull/4485)).
- **Generic AMQP 1.0 pub/sub.** The AMQP 1.0 component now also registers as `pubsub.amqp`. This form has no vendor-specific address prefix, so it works against any AMQP 1.0 broker. `pubsub.solace.amqp` keeps its original `topic://` and `queue://` prefixes. Existing Solace components keep working unchanged ([components-contrib#4602](https://github.com/dapr/components-contrib/pull/4602), [#10502](https://github.com/dapr/dapr/pull/10502)).

### Structured logging: more output destinations and file rotation

The control-plane binaries and daprd take six new logging flags, from two `dapr/kit` changes ([kit#166](https://github.com/dapr/kit/pull/166), [kit#167](https://github.com/dapr/kit/pull/167)):

- `--log-outputs`: a comma-separated list of log destinations (`stdout`, `stderr`, or a file path). It merges with `--log-file`, so an existing `--log-file` configuration is unchanged.
- `--log-file-max-size`, `--log-file-max-backups`, `--log-file-max-age` and `--log-file-compression`: rotation for file destinations. Without them, a file destination is a plain file that grows with no limit.
- `--log-timestamp-format`: a Go time layout for the log timestamp. The default, RFC3339 with nanoseconds, stays unless you set this flag.

All six flags default to off or empty, so a binary that sets none of them behaves as before.

See the [full list of changes below](#list-of-issues-addressed-in-this-release) for the rest.

## SDK Improvements

### Go SDK

The Go SDK can now host actors over gRPC ([go-sdk#828](https://github.com/dapr/go-sdk/pull/828)). The app receives actor invoke, reminder, timer and deactivate callbacks on one bidirectional stream (`SubscribeActorEventsAlpha1`), so it does not need an HTTP callback server. This uses the runtime feature from [dapr#9812](https://github.com/dapr/dapr/pull/9812) (1.18).

## List of issues addressed in this release

### Dapr Runtime

#### Security

- **FIXED** Scheduler: reject actor reminder jobs on another app's reserved internal actor types (`dapr.internal.<namespace>.<appID>.*`). An app in the same namespace could schedule, read, list or delete reminders on these actor types. With that, it could run the other app's activities and forge their results. The Scheduler now returns `PermissionDenied` for these requests. Activity result reminders between apps stay allowed [10682](https://github.com/dapr/dapr/pull/10682)
- **FIXED** Service invocation: stop forwarding caller-supplied identity headers to the target app. A calling app could set its own `dapr-caller-app-id`, `dapr-caller-namespace` or `dapr-callee-app-id` header or metadata value. A target app that read only the first value of one of these could be misled about who called it. Every sidecar now sets these values itself, from the caller's mTLS identity [10683](https://github.com/dapr/dapr/pull/10683)
- **FIXED** Service invocation: reject methods that contain `%2F`, `%5C` or `%2E` (any letter case) or a literal `\`. The access control check read these as literal characters, but the target app's HTTP server decoded them. A caller could then reach an operation that the access control policy denies. This completes the fix for CVE-2026-41491 [10684](https://github.com/dapr/dapr/pull/10684)
- **FIXED** Workflows (`WorkflowsClusteredDeployment` preview): only sidecars of the owning app can call its reserved executor and retentioner actors. Before, another app in the same namespace could forge workflow and activity task results through the executor actor. A deny-all `WorkflowAccessPolicy` and history signing did not stop it [10685](https://github.com/dapr/dapr/pull/10685)

## Upgrading to Dapr 1.19

To upgrade to this release of Dapr, follow the steps below to ensure a smooth upgrade.

### Local Machine / Self-hosted

Uninstall Dapr using the CLI you currently have installed. Note that this will remove the default `$HOME/.dapr` directory, binaries and all containers `dapr_redis`, `dapr_placement` and `dapr_zipkin`. Linux users need to run `sudo` if `docker` command needs sudo:

```bash
dapr uninstall --all
```

Download the latest release from [here](https://github.com/dapr/cli/releases) and put the `dapr` binary in your `PATH`.

Once you have installed the CLI, run:

```bash
dapr init --runtime-version=1.19
```

Wait for the update to finish, then ensure you are using the latest version of Dapr (1.19) with:

```bash
$ dapr --version

CLI version: 1.19
Runtime version: 1.19
```

### Kubernetes

#### Upgrading from previous version

You can perform zero-downtime upgrades using both Helm 3 and the Dapr CLI.

##### Upgrade using the CLI

Download the latest release from [here](https://github.com/dapr/cli/releases) and put the `dapr` binary in your `PATH`.

To upgrade Dapr, run:

```
dapr upgrade --runtime-version 1.19 -k
```

To upgrade with high availability mode:

```
dapr upgrade --runtime-version 1.19 --enable-ha=true -k
```

`dapr upgrade -k` also applies the updated CRDs.

Wait until the operation is finished and check your status with `dapr status -k`.

*Note: Make sure your deployments are restarted to pick the latest version of the Dapr sidecar.*

##### Upgrade using Helm

Dapr 1.19 updates two CRDs: `Configuration` (new workflow latency-bucket fields in the metrics settings) and `WorkflowAccessPolicy` (the new `requires` field). `helm upgrade` does not update CRDs, so apply them first:

```
kubectl apply -f https://raw.githubusercontent.com/dapr/dapr/v1.19.0/charts/dapr/crds/configuration.yaml
kubectl apply -f https://raw.githubusercontent.com/dapr/dapr/v1.19.0/charts/dapr/crds/workflowaccesspolicy.yaml
```

If you upgraded from 1.17 with Helm and did not apply the 1.18 CRDs, also apply `mcpservers.yaml` from the same location.

Then upgrade the chart:

```
helm repo add dapr https://dapr.github.io/helm-charts/
helm repo update

helm upgrade dapr dapr/dapr --version 1.19 --namespace=dapr-system --wait
```

Wait until the operation is finished and check your status with `dapr status -k`.

*Note: Make sure your deployments are restarted to pick the latest version of the Dapr sidecar.*

#### Starting a fresh install on a cluster

See [how to deploy Dapr on a Kubernetes cluster](https://docs.dapr.io/operations/hosting/kubernetes/kubernetes-deploy/) for a complete guide to installing Dapr on Kubernetes.

You can use Helm 3 to install Dapr:

```
helm repo add dapr https://dapr.github.io/helm-charts/
helm repo update

kubectl create namespace dapr-system

helm install dapr dapr/dapr --version 1.19 --namespace dapr-system --wait
```

Alternatively, you can use the latest version of CLI:

```
dapr init --runtime-version=1.19 -k
```

##### Post Installation

Check that the control plane pods are running and healthy:

```
$ dapr status -k
  NAME                   NAMESPACE    HEALTHY  STATUS   REPLICAS  VERSION  AGE  CREATED
  dapr-sidecar-injector  dapr-system  True     Running  1         1.19   15s  2026-10-13 09:00.00
  dapr-sentry            dapr-system  True     Running  1         1.19   15s  2026-10-13 09:00.00
  dapr-operator          dapr-system  True     Running  1         1.19   15s  2026-10-13 09:00.00
  dapr-placement         dapr-system  True     Running  1         1.19   15s  2026-10-13 09:00.00
  dapr-scheduler         dapr-system  True     Running  1         1.19   15s  2026-10-13 09:00.00
```

After Dapr 1.19 has been installed, perform a rolling restart for your deployments to pick up the new version of the sidecar:

```
kubectl rollout restart deploy/<deployment-name>
```

##### Opt-in: Placement served by the Scheduler

The opt-in Helm value `global.scheduler.placement.enabled` (default `false`) makes the Scheduler service serve actor placement, instead of the standalone Placement service. Turn it on only when every sidecar in the cluster runs 1.19 or later. An older sidecar can use only the Placement service, and the schedulers do not serve placement while an older sidecar is connected. You can turn the value on or off without sidecar restarts.

```yaml
global:
  scheduler:
    placement:
      enabled: true # default: false
```

## Downgrading to Earlier Versions

1.19 adds no new compatibility floor, such as the Ed25519 key change in 1.18. Use a standard Helm rollback:

```bash
# Helm: list revisions, then roll back to the desired one
helm history dapr -n dapr-system
helm rollback dapr <REVISION> -n dapr-system --wait

# Or pin a specific version
helm upgrade dapr dapr/dapr --version 1.18.5 --namespace dapr-system --wait
```

If you turned on `global.scheduler.placement.enabled`, turn it off before you downgrade below 1.19. Sidecars then use the redeployed Placement service, with no restarts.

If you created `WorkflowAccessPolicy` rules that use `requires`, a 1.18 control plane and sidecar do not know that field and apply those rules without the gate. Remove or narrow those rules before you downgrade.

## Breaking Changes

The changes below can require action when you upgrade from 1.18 to 1.19. The Dapr runtime API changes in 1.19 are additive. Most items here are behavior changes or SDK changes.

### Dapr runtime and Kubernetes

- **Helm upgrades: apply the 1.19 CRDs first.** `helm upgrade` does not update CRDs. Until the 1.19 `WorkflowAccessPolicy` CRD is applied, the API server drops the new `requires` field, so a rule written with `requires` applies without that gate. See [Upgrading to Dapr 1.19](#upgrading-to-dapr-119).
- **Scheduler RBAC requests read access to pods.** The Scheduler ClusterRole (or Role, in namespaced RBAC mode) now also requests `get`, `list` and `watch` on `pods`. It keeps its `namespaces` permission. The Helm chart applies this on upgrade. If you manage RBAC outside the chart, or run policy checks against minimal RBAC scopes, account for the new permission.
- **Dapr Kubernetes Services set `appProtocol`.** Every port of every Service that Dapr creates now declares `appProtocol` (`http`, `grpc`, `tls`, `https` or `tcp`). A service mesh that selects proxy behavior from this field can now treat these ports differently. Ports that carry gRPC inside Dapr mTLS are declared `tls`. [#10232](https://github.com/dapr/dapr/pull/10232)
- **Workflow: `AlreadyExists` for a duplicate active instance ID.** Through an SDK workflow client, scheduling a workflow with a running instance's ID now fails. It fails with the gRPC `AlreadyExists` status code. Before 1.19, it failed with an unclassified error. The error message is unchanged. Code that branches on the status code must handle `AlreadyExists`. [#10153](https://github.com/dapr/dapr/pull/10153)
- **Workflow: no `output` for a failed workflow.** The workflow Get API no longer copies the failure message into `dapr.workflow.output` for a workflow in the `FAILED` state. Read `dapr.workflow.failure.error_message` and `dapr.workflow.failure.error_type` instead. [#10138](https://github.com/dapr/dapr/pull/10138)
- **Scheduler retries instead of exiting.** When the embedded store of the Scheduler is briefly unavailable, the Scheduler now retries in the process. It uses a jittered backoff. Meanwhile, its healthz endpoint reports not ready. It no longer exits and restarts. Alerts that count Scheduler pod restarts no longer see this condition. Use readiness or the logs instead. [#10345](https://github.com/dapr/dapr/pull/10345)
- **Actor timers: only the owning host accepts timer operations.** A timer operation now fails on a sidecar that does not own the actor. The error is `ERR_ACTOR_TIMER_NOT_OWNED` (HTTP 403, gRPC `PermissionDenied`). In 1.18 the same call succeeded and could leak a timer. This can surface during actor rebalancing. [#10380](https://github.com/dapr/dapr/pull/10380)
- **Bounded actor reminder and timer span names.** The reminder and timer HTTP endpoints now emit span names in the form `<operation>Actor<Reminder|Timer>/<actorType>`, for example `RegisterActorReminder/OrderActor`. The span name no longer contains the actor ID or the reminder or timer name. Update dashboards and alerts that match the old span names. [#10141](https://github.com/dapr/dapr/pull/10141)
- **`--healthz-listen-address` is honored.** Placement, Scheduler, Sentry, the sidecar injector and the operator now bind their healthz server to the address in this flag. Before 1.19 the flag had no effect, and the server always bound all interfaces. [#10394](https://github.com/dapr/dapr/pull/10394)
- **Service invocation: caller identity headers come from the sidecar.** With mTLS on, the target app gets `dapr-caller-app-id` and `dapr-caller-namespace` only from its own sidecar. The sidecar sets them from the caller's mTLS identity, and it removes any value that the calling app sets. Calls through the gRPC proxy now also carry `dapr-caller-namespace` [#10683](https://github.com/dapr/dapr/pull/10683)
- **Service invocation: some encoded methods fail.** A method with `%2F`, `%5C`, `%2E` (any letter case) or a literal `\` now fails before the access control check. This covers the HTTP and gRPC APIs, calls between sidecars, proxied gRPC calls and actor method invocation [#10684](https://github.com/dapr/dapr/pull/10684)
- **Actor invoke API rejects reserved actor types.** gRPC `InvokeActor` and HTTP `/v1.0/actors/{type}/{id}/method/{method}` now reject every `dapr.internal.*` actor type. The error is `ERR_ACTOR_TYPE_RESERVED` (gRPC `PermissionDenied`, HTTP 403). The actor state, reminder and timer APIs already did this [#10685](https://github.com/dapr/dapr/pull/10685)

### Components

- **Azure Event Hubs pub/sub and input binding: checkpoints move only past successfully handled events.** Before, the checkpoint could move past a failed batch. Now the component retries a failed batch with the `backOff*` settings until the handler succeeds. `backOffMaxRetries` no longer stops the retries, so an event that always fails holds the checkpoint of its partition. In the concurrent mode (`enableInOrderMessageDelivery: false`), the new `maxConcurrentHandlers` option (default `100`) limits the batches per partition that wait for a checkpoint. At that limit, the component pauses receives for the partition. A consumer group with no stored checkpoint now starts from the earliest retained event, not the latest. The same change is in 1.18.5 ([components-contrib#4606](https://github.com/dapr/components-contrib/pull/4606)). [components-contrib#4598](https://github.com/dapr/components-contrib/pull/4598)
- **Redis pub/sub: `redeliverInterval` is honored.** A duration string such as `"30s"` was ignored, and the component always used 15 seconds. The configured value now applies. Components that do not set this field are not affected. [components-contrib#4601](https://github.com/dapr/components-contrib/pull/4601)
- **Azure App Configuration: `retryDelay` is honored.** The setting now controls the initial retry delay as documented. Before 1.19 the component used `maxRetryDelay` instead, so expect faster first retries. [components-contrib#4461](https://github.com/dapr/components-contrib/pull/4461)
- **Pub/sub: inbound retries stop when the component cancels the handler.** Inbound retries now use the handler's own context. Before 1.19, they used a context that never ended. A Kafka rebalance, for example, now stops the retries and the in-flight app call. The consumer that takes the partition then gets the message again. Azure Service Bus (`handlerTimeoutInSec`, default 60 s) and Redis Streams (`processingTimeout`, default 60 s) put a timeout on the handler. That timeout now also limits these retries. A message that exceeds it goes to the dead-letter topic, as on the bulk path. The same change is in 1.18.5. [#10497](https://github.com/dapr/dapr/pull/10497)
- **Anthropic conversation: new default model.** The default model is now `claude-sonnet-4-6`, because the previous default model is retired. To keep a specific model, set `model` in the component metadata. [components-contrib#4532](https://github.com/dapr/components-contrib/pull/4532)

### Python SDK

- **Extension packages are no longer published separately.** Remove these packages from your project: `dapr-ext-fastapi`, `dapr-ext-grpc`, `dapr-ext-langgraph`, `dapr-ext-strands`, `dapr-ext-workflow` and `flask-dapr`. Then install the matching extras of the core package, for example `pip install "dapr[fastapi,workflow]"`. Uninstall the old packages before you reinstall `dapr`. [python-sdk#1054](https://github.com/dapr/python-sdk/pull/1054)
- **Higher minimum `protobuf` and `grpcio` versions.** The SDK needs `protobuf` 6.33.5 or later and `grpcio` and `grpcio-status` 1.81.1 or later. [python-sdk#1126](https://github.com/dapr/python-sdk/pull/1126)
- **`when_all` waits for every task.** A failing `when_all` now reports the first failure only after all tasks finish. [python-sdk#1166](https://github.com/dapr/python-sdk/pull/1166)
- **Actor `get_state_names` during a transaction.** The method now excludes only keys marked for removal. Earlier releases also returned removed keys and skipped updated ones. [python-sdk#1208](https://github.com/dapr/python-sdk/pull/1208)
- **Bulk publish metadata reaches plain entries.** `publish_metadata` on `publish_events` now applies to entries that do not carry their own metadata. Before 1.19 it was dropped for those entries. [python-sdk#1228](https://github.com/dapr/python-sdk/pull/1228)
- **`DAPR_API_TIMEOUT_SECONDS` no longer limits workflow waits.** `wait_for_workflow_start` and `wait_for_workflow_completion` ignore this setting. Without their own `timeout_in_seconds`, they wait with no time limit. If you relied on the global setting, pass `timeout_in_seconds`. [python-sdk#1244](https://github.com/dapr/python-sdk/pull/1244)

### Java SDK

- **Spring integration requires Spring Boot 4.0.** Move to Spring Boot 4.0 before you take SDK 1.19. Or stay on SDK 1.18.x with Spring Boot 3.5. The two combinations are not binary compatible and fail at runtime. [java-sdk#1772](https://github.com/dapr/java-sdk/pull/1772)
- **Separate Spring Boot 4 artifacts are removed.** Replace `dapr-spring-boot-4-starter`, `dapr-spring-boot-4-starter-test` and `dapr-spring-boot-4-autoconfigure` with the artifacts without `-4` in the name. Replace `dapr-spring-6-data` with `dapr-spring-data`, and change imports from `io.dapr.spring6.data` to `io.dapr.spring.data`. [java-sdk#1772](https://github.com/dapr/java-sdk/pull/1772)
- **`WorkflowInstanceAlreadyExistsException`.** `scheduleNewWorkflow` throws this exception for a duplicate active instance ID instead of a raw `StatusRuntimeException`. [java-sdk#1782](https://github.com/dapr/java-sdk/pull/1782)
- **Netty 4.2.** The SDK now pulls Netty 4.2.x. A project that pins Netty 4.1.x directly can get a dependency conflict. [java-sdk#1814](https://github.com/dapr/java-sdk/pull/1814)

### Workflow history cache in the Python, Java and .NET SDKs

Workflow workers built with the 1.19 Python, Java or .NET SDK keep each workflow's history in memory between turns. This cache is on by default. If worker memory is limited, disable it with `disable_stateful_history` (Python), `withStatefulHistoryDisabled` (Java) or `DisableStatefulHistory` (.NET). [python-sdk#1112](https://github.com/dapr/python-sdk/pull/1112), [java-sdk#1777](https://github.com/dapr/java-sdk/pull/1777), [dotnet-sdk#1862](https://github.com/dapr/dotnet-sdk/pull/1862)

### JavaScript SDK

- **New workflow engine.** The SDK replaced its workflow engine and wire-protocol handling. `WorkflowContext`, `DaprWorkflowClient` and `WorkflowState` keep their public method names, but re-test workflow code after you upgrade. [js-sdk#857](https://github.com/dapr/js-sdk/pull/857)
- **`grpcOptions` on `DaprWorkflowClient`.** Only message-size options still take effect. Keepalive, credential, compression and other grpc-js settings are ignored without an error. [js-sdk#857](https://github.com/dapr/js-sdk/pull/857)

### Dapr CLI

- **Workflow activity job names end in `::0`.** On a 1.19 runtime, `dapr scheduler list`, `get` and `delete` show workflow activity jobs as `activity/<app-id>/<instance-id>::<task-id>::0`. Earlier runtimes used a per-execution counter in the last component, for example `::1`. Update scripts that build these names. [dapr#10283](https://github.com/dapr/dapr/pull/10283), [dapr#10504](https://github.com/dapr/dapr/pull/10504)
- **Errors and warnings go to stderr.** `init`, `list`, `uninstall`, `version` and the workflow subcommands now write error and warning messages to stderr. The `-o json` output then stays parseable. Exit codes are unchanged. Update scripts that read these messages from stdout. [cli#1673](https://github.com/dapr/cli/pull/1673)

## Deprecation Notices

- **Standalone Placement service.** Starting with 1.19, the Scheduler can serve actor placement, enabled with `global.scheduler.placement.enabled=true` (`false` by default). The standalone Placement service is planned for deprecation in Dapr v1.21, when the Scheduler serves actor placement by default. No action is required in 1.19. See the [Placement service](https://docs.dapr.io/concepts/dapr-services/placement/) docs.
- **Python SDK: CloudEvents handler type in `dapr.ext.grpc`.** Annotate topic handlers with the `SubscriptionMessage` type. An unannotated handler now emits a deprecation warning. From 1.20 it receives a different event object by default, and the CloudEvents-based type is removed in 1.22. [python-sdk#1118](https://github.com/dapr/python-sdk/pull/1118)
- **.NET SDK: `Dapr.Actors` is in maintenance mode.** `Dapr.Actors` now receives security fixes only, and new actor development happens in `Dapr.Actors.Next`. `Dapr.Actors` is not deprecated: existing code keeps working, and no deprecation or removal date is set.
