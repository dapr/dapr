## Duplicate Prometheus metric samples after a hot reload restarted the sidecar runtime

### Problem

After the sidecar restarted its runtime in-process, every scrape of the metrics endpoint logged an error and served stale values:

```text
error gathering metrics: [from Gatherer #1] collected metric "dapr_http_server_request_count" ... was collected before with the same name and label values
```

The in-process restart is how the sidecar applies a change to a Configuration, Resiliency or HTTPEndpoint resource while hot reloading is enabled, so the errors appeared as soon as one of those resources changed.
They affected every sidecar metric family, including `dapr_http_*`, `dapr_grpc_io_*` and `dapr_component_*`, and did not clear on their own.

### Impact

You were affected if you ran a sidecar with hot reloading enabled, which is the default since v1.18.0, and changed a Configuration, Resiliency or HTTPEndpoint resource.

The metrics endpoint kept returning the values recorded by the runtime that had already been replaced, so dashboards and alerts froze at the counts reached just before the change, while the work done by the running sidecar went unreported.
Each further reload added another stale copy of every series.
Only restarting the pod cleared the errors, and the next reload brought them straight back.
Metrics were the only thing affected: the reload itself completed normally and the sidecar kept serving traffic.

### Root Cause

Each runtime records its metrics on its own OpenCensus meter, created by `daprd` for that runtime.
A started meter registers itself in a process-wide producer registry that the Prometheus collector reads on every scrape.
The meter was never stopped when its runtime shut down, so after a reload the old meter was still registered next to the new one, and the scrape saw both exporting the same series with the same labels.
The Prometheus gatherer rejects a series it has already collected, so it reported the duplicate and kept the first copy it encountered, which was as likely as not the dead runtime's.

### Solution

`daprd` now stops the meter it created for a runtime once that runtime has fully shut down, so the replacement runtime's meter is the only one exporting.
Stopping is deferred until after shutdown has completed, and measurements arriving from goroutines that are still draining are dropped rather than recorded on a stopped meter.

## Sentry trust bundle Secret mounted with restrictive file permissions

### Problem

Sentry mounted the `dapr-trust-bundle` Secret without a `defaultMode`, so its contents, including the CA issuer key, were created world readable inside the container.

### Impact

There was no practical exposure, since the Sentry image is distroless and runs a single process, so no other user in the container could read the file. Compliance tooling nonetheless flags key material mounted at the default mode.

### Root Cause

The volume specification in the Sentry Deployment omitted `defaultMode`, so Kubernetes applied its default of `0644`.

### Solution

The Secret is now mounted `0440`. Sentry reads the trust bundle through the Kubernetes API rather than from this mount, so no behaviour changes and no action is required.

## Scheduler restarted when a job was deleted or overwritten as it fired

### Problem

A Scheduler replica could exit with no fault present, logging:

```text
Fatal error running scheduler: counter not found for modRevision: 21657
```

The replica's embedded etcd member went down with it, and the replica restarted.
It happened when a job or actor reminder was deleted or overwritten at the moment it fired, which workflows do routinely: terminating a workflow deletes its timer and event reminders, and reminders are re-created under the same name.

### Impact

You were affected if you ran the Scheduler with jobs, actor reminders or workflows, which is every deployment using the Scheduler for reminders.
Each occurrence restarted the whole replica, not just the job that triggered it.
While the replica was down, sidecars connected to it got `connection refused` and `cron is closed` errors when creating or deleting reminders, and in a highly available deployment the remaining replicas lost and re-established cron leadership as it left and again as it rejoined.
Workflows and reminders retried and recovered, but the restarts were unprompted and repeated as often as the workload hit the timing.

### Root Cause

The Scheduler's job engine, [go-etcd-cron](https://github.com/diagridio/go-etcd-cron), fires a due job asynchronously to the job's lifecycle.
A delete or overwrite that landed between the job being taken off its queue and its trigger being processed closed the job first, so the trigger then found no record of the job.
The engine treated that as a fatal error and stopped, and the Scheduler exits when its job engine stops.
If the same trigger arrived slightly earlier it was already dropped harmlessly, so the outcome depended only on timing.

### Solution

The Scheduler now uses go-etcd-cron [v0.12.8](https://github.com/diagridio/go-etcd-cron/releases/tag/v0.12.8), which drops a trigger for a job that has already been deleted or overwritten and logs it, instead of stopping the engine.
A deleted or overwritten job was never meant to fire again, so no trigger is lost.

## Data races in the sidecar's Scheduler, hot reload and actor placement connections

### Problem

A sidecar built with the Go race detector reported `WARNING: DATA RACE` in three places, with no fault injected:

```text
google.golang.org/grpc.(*clientStream).CloseSend()
github.com/dapr/dapr/pkg/runtime/scheduler/internal/cluster.(*streamer).outgoing.deferwrap1()   streamer.go:106
github.com/dapr/dapr/pkg/runtime/scheduler/internal/cluster.(*streamer).receive.func1()         streamer.go:62
```

1. The Scheduler job stream was closed by two goroutines at once each time the sidecar disconnected from a Scheduler, which happens on every reconnect.
2. The hot reload streams from the Operator, for Components, Subscriptions, Configurations, HTTPEndpoints, Resiliencies, MCPServers and WorkflowAccessPolicies, were closed at shutdown while they were being re-established.
3. The actor placement in-flight call tracking was updated concurrently by an actor call finishing and by the placement connection closing.

### Impact

You were affected if you ran actors, workflows, jobs or hot reloading, which covers most deployments.

The first two races were in shutdown and reconnect paths.
They left gRPC stream state unsynchronized and could drop job results that were still being sent when a Scheduler stream ended.
A sidecar shutting down could also wait for the Operator to end each hot reload stream, rather than stopping it.

The third race could break actor placement guarantees.
When the placement connection closed, which in v1.18 happens on every placement leader change, the sidecar waits for in-flight actor calls to drain before handing actors over.
An actor call that returned after the next placement session had started could release a different call's in-flight record, so the next drain did not wait for that call and the actor could briefly run on two hosts.

### Root Cause

1. Both the receive and send goroutines of the Scheduler stream closed its send side when they exited. gRPC does not allow `CloseSend` concurrently with itself or with `Send`.
2. The hot reload loader's shutdown closed the current Operator stream before waiting for its reconnect goroutine to exit, while that goroutine was replacing the stream. The first stream was also opened with the caller's context, so shutdown could not cancel it.
3. Each in-flight claim recorded whether it had been released in a plain boolean, written by both the call and the placement loop. The tracking lock and its event loop were also returned to a pool when the placement connection closed, so a late release from the previous session could be delivered to the next session's lock.

### Solution

1. Only the send goroutine closes the Scheduler stream, once and after its last send.
2. Hot reload shutdown cancels every Operator stream, including the first one. It waits for the reconnect goroutine to exit before closing the stream.
3. A claim is released at most once, guarded by an atomic flag. The in-flight lock and its event loop are no longer reused, so a late release from a closed placement session is dropped.

## Concurrent requests to an HTTP app could finish with another request's result

### Problem

When the sidecar sent several requests to an HTTP application at the same time, a request could finish with the outcome of a different, concurrent request.
This covers every request the sidecar makes to the app over HTTP, including service invocation, actor calls, input binding events and job triggers.
A request whose connection to the app failed could be reported as successful with an empty response, while a concurrent request that succeeded failed with the other request's error.
A Server-Sent Events response from the app could be written to the caller of a different request.

### Impact

You were affected if your application uses the HTTP app protocol and the sidecar sent it more than one request at a time.
This applies whether or not an app HTTP middleware pipeline is configured.

### Root Cause

The HTTP app channel passes each request through the app HTTP middleware pipeline with its own handler.
The pipeline kept a single shared handler, which every request replaced with its own, so a request could run a concurrent request's handler and record its result in that request's state.

### Solution

The pipeline no longer keeps a shared handler. Each request runs the configured middlewares around its own handler.

## Data races in sidecar shutdown, actor and workflow deactivation, and input binding close

### Problem

A sidecar built with the Go race detector reported data races in four more places:

1. Shutting down while the sidecar was still starting its gRPC servers.
2. Deactivating an actor, for example because it was idle, while calls or reminders for it were arriving.
3. Deactivating a workflow instance while invocations for it were arriving.
4. Closing an input binding, for example on a hot reload, while it was delivering events.

### Impact

1. A gRPC server started after shutdown had begun was never closed, and kept its port bound. This matters when the sidecar restarts its runtime in-process, for example on a hot reload.
2. A call could be admitted to an actor after it had been deactivated.
3. A late invocation could run a turn on a workflow instance that had already been deactivated and removed.
4. Closing the binding could race with an incoming event.

In cases 2, 3 and 4 the Go runtime can also panic with `sync: WaitGroup misuse` or `WaitGroup is reused before previous Wait has returned`.

### Root Cause

1. The shutdown path read and closed the gRPC servers without synchronizing with the startup path that created and started them.
2. The actor's lock could admit a call after it was closed, and registered the call with a `WaitGroup` that the close was already waiting on. It also read the request's method after the HTTP actor transport had started rewriting it.
3. The workflow orchestrator registered invocations with a `WaitGroup` that deactivation could already be waiting on.
4. The input binding registered each event with a `WaitGroup` that the close could already be waiting on.

### Solution

1. Starting and closing the gRPC servers are serialized, and a server is not started once shutdown has begun.
2. A closed actor lock refuses new calls and registers calls only while it is open. It records the method once when the call arrives.
3. A workflow instance refuses invocations once deactivated, and the caller retries on a new instance.
4. Closing an input binding waits for events in flight, and refuses later events.
