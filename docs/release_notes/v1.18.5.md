## Duplicate Prometheus metric samples after a hot reload restarted the sidecar runtime

### Problem

After the sidecar restarted its runtime in-process, every scrape of the metrics endpoint logged an error and served stale values:

```text
error gathering metrics: [from Gatherer #1] collected metric "dapr_http_server_request_count" ... was collected before with the same name and label values
```

The in-process restart is how the sidecar applies a change to a Configuration, Resiliency or HTTPEndpoint resource while hot reloading is enabled, so the errors appeared as soon as one of those resources changed.
They affected every sidecar metric family, including `dapr_http_*`, `dapr_grpc_io_*` and `dapr_component_*`, and did not clear on their own.

### Impact

You were affected if you ran a sidecar with hot reloading enabled, which is the default since v1.18.0, and changed a Configuration, Resiliency or HTTPEndpoint resource.

The metrics endpoint kept returning the values recorded by the runtime that had already been replaced, so dashboards and alerts froze at the counts reached just before the change, while the work done by the running sidecar went unreported.
Each further reload added another stale copy of every series.
Only restarting the pod cleared the errors, and the next reload brought them straight back.
Metrics were the only thing affected: the reload itself completed normally and the sidecar kept serving traffic.

### Root Cause

Each runtime records its metrics on its own OpenCensus meter, created by `daprd` for that runtime.
A started meter registers itself in a process-wide producer registry that the Prometheus collector reads on every scrape.
The meter was never stopped when its runtime shut down, so after a reload the old meter was still registered next to the new one, and the scrape saw both exporting the same series with the same labels.
The Prometheus gatherer rejects a series it has already collected, so it reported the duplicate and kept the first copy it encountered, which was as likely as not the dead runtime's.

### Solution

`daprd` now stops the meter it created for a runtime once that runtime has fully shut down, so the replacement runtime's meter is the only one exporting.
Stopping is deferred until after shutdown has completed, and measurements arriving from goroutines that are still draining are dropped rather than recorded on a stopped meter.

## Sentry trust bundle Secret mounted with restrictive file permissions

### Problem

Sentry mounted the `dapr-trust-bundle` Secret without a `defaultMode`, so its contents, including the CA issuer key, were created world readable inside the container.

### Impact

There was no practical exposure, since the Sentry image is distroless and runs a single process, so no other user in the container could read the file. Compliance tooling nonetheless flags key material mounted at the default mode.

### Root Cause

The volume specification in the Sentry Deployment omitted `defaultMode`, so Kubernetes applied its default of `0644`.

### Solution

The Secret is now mounted `0440`. Sentry reads the trust bundle through the Kubernetes API rather than from this mount, so no behaviour changes and no action is required.

## Azure Event Hubs checkpointed messages regardless of whether the application processed them

### Problem

The Azure Event Hubs pub/sub and input binding components advanced (checkpointed) their Event Hubs offsets without regard to whether the application actually handled the event successfully.
`processEvents()` invoked the application through `handleAsync()`, but the error `handleAsync()` returned was discarded at the call site, leaving `UpdateCheckpoint()` with no condition to check before running.

Both delivery modes were affected, in different ways:
- With the default `enableInOrderMessageDelivery: false`, checkpointing happened fire-and-forget, independent of message delivery to the application.
- With `enableInOrderMessageDelivery: true`, the component waited for the handler to return before checkpointing, but checkpointed anyway when the handler responded `RETRY`.

### Impact

You were affected if you consumed messages through the Azure Event Hubs pub/sub component or received events through the Azure Event Hubs input binding.
An event your application returned `RETRY` for, or one still in flight when the sidecar crashed or partition ownership was lost, was checkpointed and never redelivered, silently downgrading Dapr's documented at-least-once delivery guarantee ("Dapr attempts to redeliver the message until successful delivery") to at-most-once.
No error was surfaced to the publisher or subscriber when this happened.
Sibling pub/sub components such as Kafka and Service Bus already conditioned their commit or checkpoint on successful handling; only Event Hubs did not.

### Root Cause

The error returned by `handleAsync()` had no guard condition attached to it at its call site in `processEvents()`, so `UpdateCheckpoint()` ran unconditionally after every event or batch, regardless of whether the application had acknowledged it successfully.

### Solution

The Event Hubs pub/sub and input binding components now advance a partition's checkpoint only through contiguous, successfully-handled events or batches:
- A handler failure is retried with the configured backoff until it succeeds or the subscription is cancelled, instead of being dropped and checkpointed anyway.
- Under concurrent handling, a partition's checkpoint advances only through the newest contiguous run of successful batches, and checkpoint writes for a partition are serialized so they can no longer race each other out of order.
- Checkpointing is skipped once the subscription is cancelled or partition ownership loss is observed, and a checkpoint-store failure now surfaces as an error instead of being silently swallowed.
- A new `maxConcurrentHandlers` option (default `100`) bounds how many received-but-not-yet-checkpoint-eligible events can be in flight at once, pausing further receives once the bound is reached.
- Both delivery modes now start from the earliest retained event when a consumer group has no stored checkpoint yet; an existing stored checkpoint always takes precedence.
- A new subscription-level `checkPointFrequencyPerPartition` option controls how often the checkpoint is persisted for a partition (starting with the first batch, then every N contiguous successfully-processed batches, or never if set to `0`); this only affects how far a restart may replay already-successful batches, not the correctness guarantee itself.

`enableInOrderMessageDelivery: false` remains the default and continues to control ordering only — it no longer has any bearing on whether a checkpoint requires success.

## RabbitMQ pub/sub routed a message to the dead-letter queue during graceful shutdown

### Problem

When the Dapr runtime was shutting down, a RabbitMQ pub/sub subscription handler could return `context.Canceled` after the subscription context was cancelled.
The RabbitMQ component treated that context cancellation like an application processing failure and called `Nack`.
With dead lettering enabled and `requeueInFailure` set to `false`, the message was routed to the dead-letter queue instead of being redelivered by RabbitMQ when the AMQP connection closed.

### Impact

You were affected if you used the built-in RabbitMQ pub/sub component with dead lettering enabled, `requeueInFailure` disabled, and a message was in flight while the sidecar shut down gracefully.
In that case, one in-flight message per shutdown could be moved to the dead-letter queue even though the application did not fail the message.

### Root Cause

`handleMessage` unconditionally NACKed any non-nil handler error when auto-ack was disabled.
It did not distinguish real handler failures from errors caused by the subscription context being cancelled during shutdown, so `context.Canceled` followed the same NACK path as an application error.

### Solution

RabbitMQ pub/sub now checks whether the context is done before ACKing or NACKing a failed handler result.
When shutdown cancels the context, the component leaves the delivery unacknowledged so RabbitMQ can redeliver it after the connection closes.
The listener also avoids logging expected context cancellation and deadline errors as message-handling failures.

## Kafka consumers stuck in a rebalance loop while retrying a failing message

### Problem

When a Kafka consumer group rebalanced while the sidecar was retrying a message the application kept failing, the sidecar carried on retrying it against the application after the partition had been revoked.
The consumer could not release the partition, was evicted from the group, and its rejoin triggered another rebalance.
Two consumers then passed the same message back and forth indefinitely ([dapr/components-contrib#4580](https://github.com/dapr/components-contrib/issues/4580)).

### Impact

You were affected if you consumed from the Kafka pub/sub component with an inbound resiliency retry policy, and a message kept failing in the application while a rebalance happened.
A brief interruption, such as an application health check failing for a few seconds, was enough to start the loop, and it did not stop on its own.
While it ran, the affected partitions made no progress.

### Root Cause

The inbound pub/sub resiliency runner was created from `context.Background()` instead of the context the component passes to the message handler.
For Kafka, that context is the consumer group session, which is cancelled when a rebalance starts.
Because the runner ignored it, neither the retry backoff nor the in-flight call to the application could be cancelled.

### Solution

The inbound resiliency runner is now created from the handler context, as the bulk subscribe path already did.
A rebalance now stops the retries and the in-flight call to the application, the message is left unacknowledged, and the consumer that takes over the partition receives it again.

Components that put a timeout on the handler context now also bound inbound retries by it: Azure Service Bus (`handlerTimeoutInSec`, default 60s) and Redis Streams (`processingTimeout`, default 60s).
Previously that timeout had no effect on retries; a message that exceeds it is now routed to the dead letter topic, which the bulk subscribe path already did.

## Kafka redelivered a message that had already exhausted its retry policy

### Problem

When an inbound resiliency retry policy ran out of attempts and no dead letter topic was configured, the Kafka component never committed the offset of the message it had given up on.
The consumer carried on with the next message, but the partition's committed offset stayed behind the abandoned one.
The next time the consumer group reconnected, Kafka delivered that message again and the whole retry budget was spent on it a second time ([dapr/components-contrib#4362](https://github.com/dapr/components-contrib/issues/4362)).

### Impact

You were affected if you consumed from the Kafka pub/sub component with a bounded inbound retry policy and no dead letter topic, and a message kept failing in the application.

On a busy topic the problem was mostly hidden: the next message that succeeded committed a higher offset, which closed the gap.
On a quiet one it was not, because nothing came along to move the offset past it.
Consumer lag stayed at 1, and any reconnect replayed the message: a sidecar or application restart, a pod rescheduling, or a rebalance.
Each replay ran the full retry policy again against an application that had already rejected the message.

### Root Cause

The Kafka component commits a message's offset only when the handler returns no error.
When the inbound retry policy was exhausted and no dead letter topic was configured, the runtime returned the delivery error to the component, for backwards compatibility with component-level retry.
The component could not tell that apart from a failure that should be redelivered, so it left the offset where it was.
The decision to stop trying was never recorded anywhere, and a configured dead letter topic was the only thing that reliably moved the offset past a message the runtime had given up on.

### Solution

The runtime now wraps the delivery error in `pubsub.ErrRetriesExhausted` when a bounded retry policy has run out and no dead letter topic is configured.
The Kafka component commits the offset when it sees that error and stops its own retry loop.

This means the message is discarded.
Committing the offset is what stops the redelivery, and it also means Kafka will not hand the message to any consumer again.

The change applies whether or not `consumeRetryEnabled` is set on the component.
It defaults to `true` for `pubsub.kafka`, and in that configuration the component used to retry a failing message indefinitely, so the runtime's retry policy could never be seen to run out.
A message that exhausts the policy now stops there rather than being retried forever.

## Scheduler restarted when a job was deleted or overwritten as it fired

### Problem

A Scheduler replica could exit with no fault present, logging:

```text
Fatal error running scheduler: counter not found for modRevision: 21657
```

The replica's embedded etcd member went down with it, and the replica restarted.
It happened when a job or actor reminder was deleted or overwritten at the moment it fired, which workflows do routinely: terminating a workflow deletes its timer and event reminders, and reminders are re-created under the same name.

### Impact

You were affected if you ran the Scheduler with jobs, actor reminders or workflows, which is every deployment using the Scheduler for reminders.
Each occurrence restarted the whole replica, not just the job that triggered it.
While the replica was down, sidecars connected to it got `connection refused` and `cron is closed` errors when creating or deleting reminders, and in a highly available deployment the remaining replicas lost and re-established cron leadership as it left and again as it rejoined.
Workflows and reminders retried and recovered, but the restarts were unprompted and repeated as often as the workload hit the timing.

### Root Cause

The Scheduler's job engine, [go-etcd-cron](https://github.com/diagridio/go-etcd-cron), fires a due job asynchronously to the job's lifecycle.
A delete or overwrite that landed between the job being taken off its queue and its trigger being processed closed the job first, so the trigger then found no record of the job.
The engine treated that as a fatal error and stopped, and the Scheduler exits when its job engine stops.
If the same trigger arrived slightly earlier it was already dropped harmlessly, so the outcome depended only on timing.

### Solution

The Scheduler now uses go-etcd-cron [v0.12.8](https://github.com/diagridio/go-etcd-cron/releases/tag/v0.12.8), which drops a trigger for a job that has already been deleted or overwritten and logs it, instead of stopping the engine.
A deleted or overwritten job was never meant to fire again, so no trigger is lost.

## Pub/sub subscribers did not receive the publisher's tracestate or baggage

### Problem

When an app published a message with `tracestate` or `baggage` headers, or the same keys as gRPC metadata, the subscriber received the message without them.
The trace ID reached the subscriber, so the trace stayed connected, but the `tracestate` entries and all W3C baggage were lost between publish and delivery.

A second bug affected every gRPC call to the sidecar, not only publish.
When a caller sent `traceparent` and `tracestate` instead of `grpc-trace-bin`, the sidecar ignored the `tracestate`.

### Impact

You were affected if you use pub/sub with tracing and rely on `tracestate` entries or W3C baggage reaching the subscriber.
Service invocation and output bindings already forwarded baggage and were not affected by the first bug.

### Root Cause

On publish, the sidecar stored the trace ID and `tracestate` in the CloudEvent, but not the baggage.
On delivery, it rebuilt the span context from the trace ID alone and never read the stored `tracestate`.
Over gRPC the sidecar only sent `grpc-trace-bin`, which cannot carry `tracestate`.

In the gRPC API, the code that read an incoming `tracestate` header called `SpanContext.WithTraceState` and discarded the result.
`WithTraceState` returns a new span context and leaves the original unchanged, so the `tracestate` never reached the span.

### Solution

Publishing now also stores the baggage in the CloudEvent, in a `baggage` field.
When the sidecar delivers a single message to an HTTP or gRPC subscriber, including a streaming subscription, it restores the `tracestate` and the baggage and sends them as `tracestate` and `baggage` headers or metadata.
Bulk subscriptions send many messages in one request, so they do not forward any single message's `tracestate` or baggage.

The gRPC API now keeps the incoming `tracestate`.
The gRPC calls the sidecar makes to apps and to other sidecars, for service invocation, actors, input bindings and pub/sub, now carry a `tracestate` metadata header next to `grpc-trace-bin`.

## Workflow activity results delivered to the wrong instance when the instance ID contained "::"

### Problem

A workflow whose instance ID contained the character sequence `::` never completed once it called an activity.
The activity body ran, but its result was reported to a workflow instance that did not exist, was dropped with `workflow actor instance not found when reporting activity result`, and the calling workflow stayed `RUNNING` forever.

### Impact

You were affected if you created workflows with instance IDs containing `::` through a workflow SDK client, which uses the TaskHub gRPC API.
The Dapr HTTP and gRPC workflow APIs reject such IDs on create, so workflows created through them were not affected.
Affected instances could not complete and had to be purged and recreated with a different ID.

### Root Cause

An activity runs as an actor whose ID is the parent instance ID followed by `::<task ID>::<generation>`.
The activity actor recovered the parent instance ID by cutting the actor ID at the first `::`, so an instance ID that itself contained `::` was truncated, and the activity addressed its completion to the truncated, nonexistent instance.

### Solution

The activity actor now cuts the actor ID at the last two separators, which always delimit the numeric task ID and generation, so the full parent instance ID is recovered whatever characters it contains.

## Activity result from a previous ContinueAsNew generation failed or altered the new generation

### Problem

A workflow that called `ContinueAsNew` while one of its activities was still running could end `FAILED`, or complete with the previous generation's activity output, once that activity finished.
Task IDs restart at zero on every `ContinueAsNew`, so the orphaned activity shared its task ID with the first activity of the new generation.

### Impact

You were affected if a workflow scheduled an activity, did not await it, and called `ContinueAsNew` while it was still running.
If the orphan failed, the new generation's activity with the same task ID was reported as failed and the workflow ended `FAILED`; if the orphan succeeded, its output could be delivered in place of the new generation's result.

### Root Cause

Every activity result carries the execution ID of the scheduling it resolves, and the recorded `TaskScheduled` event carries the execution ID it was dispatched under.
Admission compared the two only to decide whether the result could be folded into the running turn.
A mismatch fell through to the durable inbox and was applied to the new generation's task, and the genuine result was then discarded as a duplicate.

### Solution

An activity result whose execution ID differs from the recorded scheduling of its task ID is acknowledged and dropped before it reaches the inbox, on every admission path.
The same applies to a result whose task ID this generation passed without scheduling anything there, and to any result reaching a workflow that has already completed.

## Workflow purge left the actor serving stale state, corrupting the instance or failing its re-creation

### Problem

Purging a workflow instance deleted its state rows but only queued the actor's deactivation, and left the actor's in-memory copy of the state in place until that deactivation ran.
A reminder, a late activity result, or a raised event that reached the actor in that window ran against the pre-purge copy and saved it back.
On state stores that recreate a deleted key on write, such as Redis, that save wrote a `metadata` row declaring history rows that no longer existed.
From then on every load of the instance failed with `history key 'history-000000' declared in metadata ... but missing from state store`, the failure was treated as transient, and the instance's reminders retried about once a second indefinitely.
Purging and re-creating a workflow under the same instance ID immediately afterwards could also fail with `failed to create workflow instance: possible etag mismatch`.

### Impact

You were affected if workflows were purged while events for them could still arrive: a late activity result from a workflow that completed with activities still running, a pending wake-up reminder, or an event raised by a client.
The window is normally milliseconds but grows to seconds when the sidecar is busy deactivating other actors, and it does not close when the purge returns an error after the rows are deleted, for example when the reminder deletion failed because the Scheduler was unreachable.
Affected instances could not be loaded, re-created, or purged through the API, and their reminders retried forever until the corrupted rows were deleted from the state store by hand.

### Root Cause

The purge path deleted the rows and queued the deactivation but never invalidated the actor's cached state, and the invalidation that deactivation performs waits for the actor lock.
Any invocation that acquired the lock first ran on the cached state and its conditional save succeeded on stores that do not reject a write to a deleted key.

### Solution

A purge now invalidates the actor's cached state before it returns, unconditionally, whatever else in the purge failed.
Every invocation that follows loads from the state store, finds the instance gone, and terminates or is acknowledged without saving, and a create under the same instance ID starts a fresh instance.

## Sidecar crashed on shutdown when a streaming gRPC call arrived

### Problem

The sidecar could crash while shutting down with:

```text
panic: sync: WaitGroup is reused before previous Wait has returned
```

### Impact

You could be affected if a streaming gRPC call reached the sidecar while it was shutting down: a streaming pub/sub subscription (`SubscribeTopicEventsAlpha1`), a streaming service invocation between sidecars, or a streaming encrypt or decrypt call.
The sidecar exited with a panic instead of shutting down cleanly.

### Root Cause

The gRPC API waits for the goroutines started by in-flight streaming calls when it shuts down, but the gRPC server keeps accepting new calls until it stops.
A call starting in that window added to the same wait group the shutdown was already waiting on, which Go reports as a panic.

### Solution

Streaming calls that start once the gRPC API has begun shutting down are now rejected with `Unavailable`, instead of starting new goroutines.
Service invocation retries `Unavailable` after resolving the target app again, so these calls are retried rather than failing.

## Sidecar shutdown hung when an actor callback stream opened during shutdown

### Problem

The sidecar could hang indefinitely while shutting down.

### Impact

You could be affected if your app hosts actors over the actor callback stream (`SubscribeActorEventsAlpha1`) and opened that stream while the sidecar was shutting down, for example when the app and sidecar restart together.
The sidecar did not finish shutting down until the app closed the stream, the graceful shutdown timeout forced it to exit, or the process was killed.

### Root Cause

Registering a new callback stream waited for the stream manager to confirm the registration.
Once the manager had stopped during shutdown, the registration was silently dropped, so that confirmation never arrived.
The gRPC server waits for open calls before it stops, so it waited on the stuck registration.

### Solution

Registering a callback stream now also returns once the stream manager has stopped, so the call ends as the sidecar shuts down.

## Placement stream close hung when the placement server did not end the stream

### Problem

The sidecar could stop processing actor placement updates after it tried to close its connection to the placement service.

### Impact

You could be affected if the placement service stopped responding on an open stream, for example during a network partition.
The sidecar did not reconnect, so actor placement on that sidecar stayed stale until the placement service ended the stream or the sidecar restarted.

### Root Cause

When closing its placement stream, the sidecar signalled that it had finished sending and then waited for its receive loop to exit.
The receive loop only exits when the server ends the stream, so an unresponsive server blocked the close, and with it the loop that reconnects to placement.

### Solution

Closing the placement stream now also cancels the stream's context, which ends the receive loop without waiting on the server.


## Duplicate traceparent header on proxied gRPC service invocation

### Problem

On a proxied gRPC service invocation, when the caller provided a `traceparent`, the callee received two `traceparent` values: the caller's forwarded value and Dapr's own appended one.

### Impact

Frameworks that join same-name headers (for example ASP.NET Core) collapsed the two values into a single comma-joined header. A W3C `traceparent` is single valued, so the propagator could not parse it, discarded the context, and started a new trace, breaking the distributed trace at every hop. This was introduced in 1.16.0.

### Root Cause

`SpanContextToGRPCMetadata` used `AppendToOutgoingContext` to add the `traceparent` (and `tracestate`). On the service-invocation path the caller's `traceparent` was already on the outgoing context, so appending left a second one.

### Solution

`SpanContextToGRPCMetadata` now sets (replaces) the `traceparent`/`tracestate` on the outgoing context rather than appending, so exactly one `traceparent` survives.
## Workflow executed twice when its start request was retried

### Problem

A workflow started once could run a second time from the beginning, with the sidecar logging:

```text
Workflow actor '<instance ID>': workflow was previously completed and is being recreated
```

No client had asked to recreate it.
The second run repeated every activity and replaced the first run's history and output.
In a related symptom, starting a workflow could fail with `an active workflow with ID '<instance ID>' already exists` even though that same request had created the workflow.

### Impact

You were affected if you started workflows and a start request hit a transient failure after the workflow had already been created, such as a dropped connection, a sidecar restart or actors moving between replicas.
Short workflows were the most exposed, because they could complete before the retry arrived.

### Root Cause

Starting a workflow is retried at several layers, both inside the sidecar and in the workflow API.
A retry that arrived after the first attempt had already been saved was treated as a new request.
If the workflow had already completed, the workflow actor treated the retry as a request to reuse the instance ID, so it cleared the instance and ran the workflow again.
If the workflow was still running, the retry was rejected as a duplicate, and the workflow API then retried that rejection with a freshly generated start request every second, until the workflow completed and one of those attempts recreated it.

### Solution

Every start request carries an execution ID that is generated once and resent unchanged by each retry.
The workflow actor now compares it with the execution ID of the instance it already holds.
A match means the request is a retry of a start that already succeeded, so the actor reports success without running the workflow again.
The workflow API also no longer retries a start that was rejected because the instance already exists.
Starting a new workflow under the ID of a completed one still works as before, because every new start carries a different execution ID.

## Scheduler jobs and actor reminders created as the trigger queue emptied never fired

### Problem

A Scheduler job or actor reminder could be accepted and stored, yet never trigger.
The Scheduler stayed healthy and logged nothing for it: no trigger attempt, no error.
Jobs created before and after it fired normally, and the stuck job only fired once some unrelated job was later created on the same Scheduler replica.

The same fault could also stall the in-memory actor timers in the sidecar.

### Impact

You were affected if you ran the Scheduler, which includes every deployment using workflows or actor reminders.
The window was narrow and only hit under load, when several jobs were created at the same moment the replica's trigger queue had just drained.
Workflows were the most exposed, since every step runs through one-shot reminders and a stuck reminder stalls the instance indefinitely.
A workflow waiting on a stuck reminder made no progress until another reminder happened to be created on the same replica.

### Root Cause

The queue that fires due jobs, provided by [dapr/kit](https://github.com/dapr/kit), is served by a single background loop guarded by a "loop running" flag.
When the loop found the queue empty it exited, but it cleared that flag only after releasing the queue lock.
A job enqueued in that gap saw the flag still set, concluded a loop would pick it up, and did nothing.
The loop then finished exiting, leaving the job in the queue with no loop alive to run it.
The code had been this way since 2023.
It became reachable once the Scheduler's job engine started feeding the queue from many worker goroutines at once and workflows began creating hundreds of one-shot reminders per second.

### Solution

The loop now clears the flag while it still holds the queue lock, so a concurrent enqueue either lands before the empty check and is seen, or after the flag is cleared and starts a new loop.
A dapr/kit regression test drives concurrent enqueues against the loop exiting and checks under the lock that no job is ever queued without a loop running.

## Scheduler members stopped together left their cron leadership leases for the full lease TTL

### Problem

After a full stop and restart of a Scheduler cluster, some replicas took about 20 seconds longer than the others to report cron ready.
In a three replica cluster, two replicas reported ready about 21 seconds after the third.
Jobs and actor reminders were not lost.
They resumed once leadership was established.

### Impact

You were affected if you stopped several Scheduler replicas at the same time, as in a full cluster stop and restart.
A rolling restart was not affected.
A replica stopping on its own hands off etcd leadership before it revokes its own lease.

### Root Cause

The Scheduler's job engine, [go-etcd-cron](https://github.com/diagridio/go-etcd-cron), coordinates cron leadership between Scheduler replicas with etcd leases.
On shutdown each replica revokes its leadership lease so a replacement can take over at once.
The revoke was a single attempt with a 5 second deadline.
A timeout was treated as success.
When several replicas stopped at the same time, the etcd leader among them handed off leadership while the others were sending their revokes.
A write that reaches etcd during a leader hand-off is dropped.
It is either never answered or returned as an error with the text `raft proposal dropped`.
Those revokes timed out and the leases were never released.
An unrevoked lease stays alive in etcd for its TTL, which is 20 seconds for these leases.
A new etcd leader also resets every lease to a full TTL.
A replica restarting with the same id waited until its own stale lease expired before it could take cron leadership again.
The third replica was not delayed because its predecessor revoked after the hand-off had finished.

### Solution

The Scheduler now uses go-etcd-cron with [pull request #136](https://github.com/diagridio/go-etcd-cron/pull/136), which retries the revoke with short attempts inside a 2 second budget.
It retries on a timeout, on unavailable, and on the dropped-write error.
Any other error is returned immediately, as before.
The engine logs when the budget runs out.
A dropped revoke now completes on the next attempt about 100 milliseconds later, and the restarted cluster becomes ready in under a second.

## Conversation API requests to Anthropic failed when tool choice was set

### Problem

A Conversation API request to the Anthropic component that set `toolChoice` failed with an HTTP 400 error from the Anthropic Messages API.

### Impact

You were affected if you used the Anthropic conversation component with tools and set `toolChoice` to any value, including `auto`, `required`, `none`, or the name of a specific tool.
Requests that did not set `toolChoice` were not affected, and other conversation providers were not affected.

### Root Cause

The Anthropic Messages API expects `tool_choice` as an object, such as `{"type":"any"}`.
The conversation components forwarded the request's `toolChoice` string unchanged, which is the format OpenAI-compatible providers expect, so Anthropic rejected the request.

### Solution

The Anthropic component now translates `toolChoice` into the object Anthropic expects ([dapr/components-contrib#4542](https://github.com/dapr/components-contrib/pull/4542)):
- `auto` is omitted, since Anthropic already defaults to `{"type":"auto"}`.
- `required` and `any` become `{"type":"any"}`.
- `none` becomes `{"type":"none"}`.
- A tool name becomes `{"type":"tool","name":"<tool name>"}`.

`toolChoice` is also omitted when the request has no tools, which Anthropic rejects.
Other conversation providers are unchanged.
