# Dapr 1.17.17

This update contains the following bug fixes and improvements:
- [Redis components could not open new connections after the Entra ID token expired](#redis-components-could-not-open-new-connections-after-the-entra-id-token-expired)
- [Security: Compromised eMudhra intermediate CA keys were trusted for outbound TLS](#security-compromised-emudhra-intermediate-ca-keys-were-trusted-for-outbound-tls)

## Redis components could not open new connections after the Entra ID token expired

### Problem

With `useEntraID: true`, the Redis state store, pub/sub, binding, lock and configuration components worked until the first access token expired. After that, every new connection to Redis failed with `WRONGPASS invalid username-password pair or user is disabled`, and the component stayed broken until the sidecar was restarted.

### Impact

You were affected if a Redis component authenticated to Azure Cache for Redis or Azure Managed Redis with Microsoft Entra ID. The first token lasts about an hour for a service principal and up to 24 hours for a managed identity. Once it expired, any connection the client opened afterwards failed to authenticate, whether the pool replaced an idle or aged connection, recovered from a network interruption, or grew under load. Reporters saw every call through the component fail after the first token's lifetime, until the pod was restarted.

### Root Cause

At startup the component fetched one token and stored it as the connection password. The Redis client sends that stored password every time it opens a connection, so a connection opened after the token expired presented a token Redis no longer accepted. A background routine refreshed the token before it expired, but it only re-authenticated the single connection it ran on and never replaced the stored password.

### Solution

The component fetches a current token every time it opens a Redis connection, so connections opened after the first token expires authenticate with a valid one.

## Security: Compromised eMudhra intermediate CA keys were trusted for outbound TLS

### Problem

The private keys of eight eMudhra intermediate CA certificates were compromised and reported to the browser root programs on October 17, 2026.
Anyone holding one of these keys can issue a TLS certificate for any domain that Go programs accept as valid.
Dapr 1.17.16 and earlier were built with Go 1.26.9, which still trusts certificate chains through these intermediates.

### Impact

You were affected if daprd makes outbound TLS connections that are verified against the system trust store, such as components connecting to cloud services or service invocation to external HTTPEndpoints.
An attacker holding one of the keys and able to intercept that traffic could impersonate the remote service and read or change the data sent to it.
mTLS between sidecars and the control plane uses Dapr's own CA and is not affected.
According to the Chrome Root Program, no website certificate chaining to these intermediates had been logged to Certificate Transparency before they were blocked.

### Root Cause

Go's `crypto/x509` verifier does no revocation checks, so the compromised intermediates stayed trusted until Go itself blocked them.

### Solution

Dapr is now built with [Go 1.26.10](https://go.dev/doc/devel/release#go1.26.10), whose `crypto/x509` package rejects any certificate chain that passes through the compromised keys.
