## Actor and workflow calls kept failing after a pod IP was reused by a different app

### Problem

The sidecar keeps one gRPC connection per remote address for calls to other sidecars, such as actor invocation and workflow calls between apps.
The mTLS credentials of a connection pin the namespace and app ID of the peer it was created for, and gRPC reuses them every time the connection reconnects.
The connection pool was keyed by address only.
When Kubernetes gave the IP of a stopped pod to a pod of a different app, the sidecar kept using the connection created for the previous app.
Every handshake failed with `unexpected SPIFFE ID`, and every actor or workflow call to the new app on that address failed with `Unavailable`.

### Impact

You were affected if mTLS is enabled, your apps call actors or workflows on a remote app, and the IP of a pod was reused by a pod of a different app.
Calls from a sidecar to that address kept failing until the sidecar stopped calling it for 3 minutes (`DAPR_GRPC_MAX_CONN_IDLE`) or the target pod got a new IP.
With steady traffic, that did not happen. Calls to other pods of the same app were not affected.
Deleting the pod that received the reused IP recovered it.

### Root Cause

The pool looked up an existing connection by address, and the identity the connection expects was not part of the lookup.
Before Dapr 1.15 the actor call path closed the connection when a call failed with `Unavailable`, which hid the problem.
Since 1.15 it does not, and nothing else closes a connection that is in use.
Service invocation and the gRPC proxy still close the connection on `Unavailable`, so they recovered.

### Solution

The connection pool is now keyed by address, namespace and app ID.
A sidecar that finds a different app at an address it has used before dials a new connection with the credentials for that app.
Connections to the same address, namespace and app ID are still shared.
When a sidecar dials a new connection to an address, it also closes the idle connections it holds there for other apps, which can no longer succeed. Connections that are in use are left to finish.

## Actor sidecars stopped becoming ready after a sidecar without an actor state store joined

### Problem

The Placement service could stop sending placement tables in a namespace.
After that, every new sidecar in the namespace waited for its table and never became ready, and actor placement in the namespace stopped changing.
The Placement service did not recover on its own.

### Impact

You were affected if an app declares actor types but has no actor state store, and its sidecar connects to Placement when only one other sidecar with actors is connected in the namespace.
New sidecars in that namespace did not become ready until the Placement leader restarted.

### Root Cause

A sidecar that declares actor types but has no actor state store reports its host to Placement twice when it connects.
Placement answers each report with a copy of the placement table sent to that sidecar only, and ignores the sidecar's acknowledgements of that copy.
After the second copy, Placement counted the sidecar's acknowledgements as part of a namespace-wide update that was not running.
With two sidecars in the namespace, that was enough to finish the phantom update, and Placement asked the other sidecar to unlock with no timeout set.
The other sidecar ignored that request because it was out of sequence, and Placement waited for its answer indefinitely.

### Solution

Placement now counts an acknowledgement only when it is for the current step of the update.

## Workflows and activities with per-name concurrency limits stalled in the Scheduler

### Problem

When a workflow or activity name had a per-name concurrency limit and the matching global limit was also set, work waiting for a free slot was not started when a running instance completed.
It stayed queued until some unrelated workflow or activity of the same type completed.

### Impact

You were affected on Dapr 1.19.0 and 1.19.1 if, in the `workflow` section of the Dapr Configuration, you set a per-name limit together with the global limit of the same kind:
`workflowConcurrencyLimits` with `globalMaxConcurrentWorkflowInvocations`, or `activityConcurrencyLimits` with `globalMaxConcurrentActivityInvocations`.
Per-name limits set without the matching global limit were not affected.
Workflows and activities with those names ran far below their configured limit. With a per-name limit of 1, only 1 of 10 queued activities ran in about 45 seconds.

### Root Cause

With both limits set, a workflow or activity holds two concurrency gates in the Scheduler: one for its type (the global limit) and one for its name (the per-name limit). Waiting work queues on the type gate.
When an instance completed, the Scheduler released the type gate and tried to start waiting work before it released the name gate. That attempt failed because the name gate was still held, and the work was queued again.
Releasing the name gate a moment later did not retry it, so the work waited for the next unrelated release.

### Solution

The Scheduler releases all the gates held by a completed workflow or activity before it tries to start waiting work.

## Cross-app child workflows never completed when the parent app had a workflow access policy

### Problem

When a workflow called a child workflow on another app, and a `WorkflowAccessPolicy` applied to the parent workflow's app, the parent never received the child's result.
The child completed, but the parent stayed `RUNNING` indefinitely, and the child kept re-sending its result on a reminder.
The parent's sidecar rejected every delivery with `access denied by workflow access policy: malformed request for method 'AddWorkflowEvent'`.

### Impact

You were affected on Dapr 1.19.0 and 1.19.1 if a `WorkflowAccessPolicy` applied to an app and a workflow of that app called a child workflow on another app.
Every such parent workflow waited for its child indefinitely.
No rule in the policy could let the result through, so removing the policy from the parent app was the only workaround.
Workflows that called activities on another app were not blocked. The activity result was rejected in the same way, but then reached the parent through the activity result reminder. Each rejection still logged a warning and incremented `dapr_runtime_workflow_acl_action_denied_total`.

### Root Cause

The parent's sidecar checks every call from another app against its workflow access policy.
It works out the operation from the type of history event the call carries, and it only recognised terminate, raise event, pause and resume.
A child workflow's completion or an activity's result is none of these, so the check treated the call as malformed and denied it before evaluating any rule.

### Solution

The parent's sidecar no longer evaluates a child workflow's completion or an activity's result against the policy rules.
These are replies to tasks the parent workflow dispatched, not operations another app performs on it.
Instead, the parent accepts a result from another app only when the task was dispatched to that app, and denies it from any other app.
The parent still verifies the result's attestation when workflow history signing is on.
Only the sidecar of the parent's app needs the upgrade. After it, the child's next retry delivers the result and stuck parent workflows continue on their own.

## Bulk publish ignored request-level metadata for entries without their own metadata

### Problem

When publishing events in bulk, metadata set on the request, such as `ttlInSeconds` or `partitionKey`, was only applied to entries that also carried metadata of their own.
Entries with no metadata were published without the request-level metadata.
For example, publishing two entries with `ttlInSeconds=300` on the request, where only the first entry set its own `partitionKey`, produced a cloud event with an `expiration` field on the first entry and none on the second.

### Impact

You were affected on Dapr 1.19.0 and 1.19.1, and on earlier releases, if you used the bulk publish API over HTTP or gRPC with request-level metadata.
Most SDK bulk publish calls, such as `PublishEvents` in the Go SDK and `publish_events` in the Python SDK, build entries with no per-entry metadata, so for those callers request-level metadata had no effect at all.
On components whose message TTL is handled by Dapr rather than natively, such as Redis, messages published with only a request-level `ttlInSeconds` never expired.
Other request-level keys that a component reads per message, such as a partition key, were not applied either.
The only workaround was to repeat the metadata on every entry.

### Root Cause

The HTTP and gRPC bulk publish handlers merged request-level metadata into an entry only when the entry already had a metadata map.
An entry with no metadata had none, so the merge was skipped and no request-level key reached it.
The merge itself already handled an entry without metadata correctly; only the guard around it skipped the call.

### Solution

Both handlers now merge request-level metadata into every entry.
Entry-level keys keep precedence over request-level keys, matching the documented behavior of bulk publish and of the single publish API.
`rawPayload` is still read from request-level metadata before the entries are processed and is unaffected.

## Security: go-jose denial of service

### Problem

An upstream dependency of Dapr, `github.com/go-jose/go-jose/v4`, had three vulnerabilities in v4.1.4:

- [CVE-2026-116587](https://github.com/go-jose/go-jose/security/advisories/GHSA-mgcc-cww5-fp2q) (high): denial of service when go-jose parses a JWK that contains an RSA key.
- [CVE-2026-116586](https://github.com/go-jose/go-jose/security/advisories/GHSA-vvm8-gf78-28g4) (medium): a crash during JSON parsing.
- [CVE-2026-116585](https://github.com/go-jose/go-jose/security/advisories/GHSA-4w3g-jfj2-cw2q) (medium): a panic during CBC-HMAC processing.

### Impact

Dapr calls go-jose only through `go-spiffe`. It parses the JWKS in the trust bundle when the trust anchors load, and it parses the JWT that Sentry issues to the sidecar. These inputs come from the Dapr control plane, not from application requests.

CVE-2026-116587 and CVE-2026-116586 are on these paths in daprd and in each control plane service. Both are denial of service. CVE-2026-116585 is in JWE decryption, which Dapr does not use.

### Root Cause

Dapr pinned go-jose at v4.1.4. go-jose v4.1.5 fixes CVE-2026-116586 and CVE-2026-116585, and v4.1.6 fixes CVE-2026-116587.

### Solution

This release upgrades `github.com/go-jose/go-jose/v4` from v4.1.4 to v4.1.6.

go-jose v4.1.6 rejects an RSA key with a modulus larger than 4096 bits in a JWK. This affects you only if both of these conditions are true:

- JWT issuing is on in Sentry.
- You supply your own RSA JWT signing key that is larger than 4096 bits.

In that case, daprd and the control plane services cannot load the trust bundle, and they stop with the error `failed to parse JWT bundle`. Before you upgrade, replace the key with an RSA key of 4096 bits or fewer, or with an EC key. The JWT signing key that Sentry generates is RSA-2048, and it is not affected.

## Security: brotli denial of service

### Problem

An indirect dependency of Dapr, `github.com/andybalholm/brotli`, had a vulnerability in v1.2.1:

- [CVE-2026-111497](https://github.com/andybalholm/brotli/security/advisories/GHSA-c9gr-gmg4-2vqv) ([GO-2026-6888](https://pkg.go.dev/vuln/GO-2026-6888)): the brotli decompressor did not limit the memory that it allocates for each meta-block. A small crafted brotli stream can make it allocate hundreds of megabytes for each kilobyte of input. This causes a denial of service.

### Impact

Dapr uses brotli only through the Meilisearch search component (`search.meilisearch`) and its `meilisearch-go` client.
That client decompresses brotli data only when the code that creates the client sets a content encoding.
The Dapr Meilisearch component does not set a content encoding, so Dapr does not decompress brotli data.

Vulnerability scanners and `govulncheck` report this vulnerability for Dapr 1.19.0 and 1.19.1, because both releases include brotli v1.2.1.

### Root Cause

Dapr pinned brotli at v1.2.1. brotli v1.2.7 fixes CVE-2026-111497.

### Solution

This release upgrades `github.com/andybalholm/brotli` from v1.2.1 to v1.2.7.
