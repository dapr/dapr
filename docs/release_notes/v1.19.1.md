# Dapr 1.19.1

This update contains the following bug fixes and improvements:
- [Sidecar leaked connections while the Placement service was unreachable](#sidecar-leaked-connections-while-the-placement-service-was-unreachable)
- [Security: Service invocation access control bypass with other percent-encoded characters and path parameters](#security-service-invocation-access-control-bypass-with-other-percent-encoded-characters-and-path-parameters)

## Sidecar leaked connections while the Placement service was unreachable

### Problem

While the sidecar could not reach the Placement service, it tried to connect about twice a second. Each attempt opened a new gRPC connection, and the sidecar did not close it when the attempt failed. Each leaked connection kept trying to reach Placement, with its own goroutines, until the sidecar restarted.
The sidecar also did not close the connection when a stream to Placement ended.

### Impact

You were affected if a sidecar could not reach the Placement service for a sustained period, for example while its pods restarted or crash looped. The goroutine count and memory use of every sidecar that connects to Placement grew for as long as the outage lasted. In a test with Placement stopped, the goroutine count of the sidecar grew by about 8 every second. Restarting the sidecar released the connections.

### Root Cause

The sidecar dials a connection to a Placement host and then opens the Placement stream on it. The dial does not wait for the host, so it succeeds while Placement is down, and only opening the stream fails.
When opening the stream failed, the sidecar returned the error without closing the connection, and the retry loop dialed another one. When a stream ended, the sidecar cancelled the stream but did not close its connection.

### Solution

The sidecar closes the connection when opening the stream fails, and closes it when the stream ends.

## Security: Service invocation access control bypass with other percent-encoded characters and path parameters

### Problem

Service invocation access control policies match the invoked method literally, after lowercasing it for HTTP apps.
The method is sent to an HTTP app unchanged, and the app's HTTP server decodes percent-encoded characters before routing.
A method that percent-encoded any other character, such as `%61dmin/secret`, therefore did not match a rule for `/admin/secret`, but the app decoded it to `/admin/secret`.
Some HTTP servers, such as Java servlet containers, also drop `;` path parameters before routing, so `admin;x/secret` reached `/admin/secret` on those apps.

This completes the fix for "Security: Service invocation access control bypass with percent-encoded path characters" in Dapr 1.17.16 and 1.18.6, which only covered `%2F`, `%5C` and `%2E`.

### Impact

You were affected if you used service invocation access control policies with a deny-list (`defaultAction: allow` and operations set to `action: deny`), and the target application uses the HTTP app protocol.
An attacker needs an application identity that the policy allows to call the target.
They could invoke a denied operation such as `/admin/secret` by sending the method `%61dmin/secret` through the gRPC API, or `%2561dmin/secret` through the HTTP API.
On apps that drop `;` path parameters, `admin;x/secret` worked as well.
Allow-list policies (`defaultAction: deny`) were not affected, because an encoded method matched no allow rule.

Reported by Lee SeongHyeon.

### Root Cause

The access control check compared the method as a literal string, while the HTTP app routes on the decoded path without `;` parameters.
The earlier fix rejected only the encoded characters that change how the path splits into segments, and passed all other percent-encoded sequences through.

### Solution

For HTTP apps, the access control check now matches policies against the method as the app routes it: percent-encoded characters decoded once, `;` parameters removed from each path segment, then lowercased.
A request whose method has an invalid percent-escape is denied.
Operations in access control policies are read the same way, so existing rules keep matching.
The method sent to the app is not changed, so applications that use encoded characters in method names keep working.
gRPC apps are unchanged.

Allow rules now also match encoded spellings of the allowed path, and spellings with `;` parameters, for example `/public;x` for a `/public` rule.
A policy operation that contains `;` now ends at the `;`, and a `%2A` in a policy operation now acts as the `*` wildcard.
