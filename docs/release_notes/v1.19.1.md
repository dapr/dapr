## Sidecar leaked connections while the Placement service was unreachable

### Problem

While the sidecar could not reach the Placement service, it tried to connect about twice a second. Each attempt opened a new gRPC connection, and the sidecar did not close it when the attempt failed. Each leaked connection kept trying to reach Placement, with its own goroutines, until the sidecar restarted.
The sidecar also did not close the connection when a stream to Placement ended.

### Impact

You were affected if a sidecar could not reach the Placement service for a sustained period, for example while its pods restarted or crash looped. The goroutine count and memory use of every sidecar that connects to Placement grew for as long as the outage lasted. In a test with Placement stopped, the goroutine count of the sidecar grew by about 8 every second. Restarting the sidecar released the connections.

### Root Cause

The sidecar dials a connection to a Placement host and then opens the Placement stream on it. The dial does not wait for the host, so it succeeds while Placement is down, and only opening the stream fails.
When opening the stream failed, the sidecar returned the error without closing the connection, and the retry loop dialed another one. When a stream ended, the sidecar cancelled the stream but did not close its connection.

### Solution

The sidecar closes the connection when opening the stream fails, and closes it when the stream ends.

## SQLite state store writes failed with `database is locked` after a cancelled read

### Problem

After a read from the SQLite state store was cancelled, a later write on the same connection could fail at once with `database is locked` (`SQLITE_BUSY`).
The write did not wait for the configured `busyTimeout`. The error continued while that connection stayed in the connection pool.

### Impact

You were affected if you use the SQLite state store, also as the actor or workflow state store, and requests to it are cancelled.
For example, a client timeout, a workflow worker that disconnects, or a sidecar shutdown cancels requests.
Workflow starts, raised events and state writes could fail with this error.

### Root Cause

The SQLite driver, `modernc.org/sqlite` v1.34.5, did not close the rows of a query when the query context was cancelled after the first row was returned.
The connection kept its read transaction open and went back to the pool.
SQLite does not wait for the busy timeout when the connection already holds a read transaction.
So the next write transaction on that connection failed at once.

### Solution

Dapr now uses `modernc.org/sqlite` v1.42.2.
This version closes the rows of a cancelled query.
It also fixes a cancelled context that interrupted a later, unrelated query on the same connection.

## Security: Service invocation access control bypass with other percent-encoded characters and path parameters

### Problem

Service invocation access control policies match the invoked method literally, after lowercasing it for HTTP apps.
The method is sent to an HTTP app unchanged, and the app's HTTP server decodes percent-encoded characters before routing.
A method that percent-encoded any other character, such as `%61dmin/secret`, therefore did not match a rule for `/admin/secret`, but the app decoded it to `/admin/secret`.
Some HTTP servers, such as Java servlet containers, also drop `;` path parameters before routing, so `admin;x/secret` reached `/admin/secret` on those apps.

This completes the fix for "Security: Service invocation access control bypass with percent-encoded path characters" in Dapr 1.17.16 and 1.18.6, which only covered `%2F`, `%5C` and `%2E`.

### Impact

You were affected if you used service invocation access control policies with a deny-list (`defaultAction: allow` and operations set to `action: deny`), and the target application uses the HTTP app protocol.
An attacker needs an application identity that the policy allows to call the target.
They could invoke a denied operation such as `/admin/secret` by sending the method `%61dmin/secret` through the gRPC API, or `%2561dmin/secret` through the HTTP API.
On apps that drop `;` path parameters, `admin;x/secret` worked as well.
Allow-list policies (`defaultAction: deny`) were not affected, because an encoded method matched no allow rule.

Reported by Lee SeongHyeon.

### Root Cause

The access control check compared the method as a literal string, while the HTTP app routes on the decoded path without `;` parameters.
The earlier fix rejected only the encoded characters that change how the path splits into segments, and passed all other percent-encoded sequences through.

### Solution

For HTTP apps, the access control check now matches policies against the method as the app routes it: percent-encoded characters decoded once, then lowercased.
Some HTTP servers drop `;` path parameters before routing and others do not, so the method must be allowed both with and without its `;` parameters.
A request is denied if its method has an invalid percent-escape, or if removing `;` parameters leaves an empty, `.` or `..` path segment, as with `..;x`.
An encoded `*` (`%2A`) is not decoded, so it never acts as a wildcard.
Operations in access control policies are read the same way, so existing rules keep matching.
If several operations in a policy resolve to the same path, their rules are combined, and `deny` wins where they conflict.
The method sent to the app is not changed, so applications that use encoded characters in method names keep working.
gRPC apps are unchanged.

Allow rules now also match encoded spellings of the allowed path, for example `/%70ublic` for a `/public` rule.
A policy operation that contains `;` now ends at the `;`.

## Security: Scheduler delivered another app's workflow reminders to any app in the namespace

### Problem

When a sidecar connects to the Scheduler to receive job and reminder triggers (`WatchJobs`), it declares the actor types it hosts and per actor type concurrency limits.
The Scheduler checked that the caller's identity matched the app ID and namespace in the request, but not that the caller owned the declared actor types.
An app could declare another app's reserved internal actor types, such as `dapr.internal.<namespace>.<app ID>.workflow` and `dapr.internal.<namespace>.<app ID>.activity`.
The Scheduler then delivered a share of that app's workflow and activity reminder triggers to it, and applied its concurrency limits to the other app's actor types.

### Impact

Any workload with a Dapr identity for an app in a namespace could call the Scheduler directly and receive workflow and activity reminder triggers of other apps in the same namespace.
The triggers include the reminder data, such as workflow inputs and history events.
By acknowledging the triggers without acting on them, or by setting a low concurrency limit, it could also stall those workflows.
Other namespaces were not affected.

### Root Cause

Job and reminder management and actor placement already reject internal actor types that do not belong to the calling app.
The `WatchJobs` stream setup did not apply the same check to the actor types and concurrency limits it registers.

### Solution

The Scheduler now rejects a `WatchJobs` stream with `PermissionDenied` if it declares, or sets a concurrency limit on, an internal actor type (`dapr.internal.*`) that does not belong to the calling app and namespace.
Sidecars only declare their own internal actor types, so they are not affected. User-defined actor types are unchanged.

## Security: API token check bypassed with a percent-encoded health check path

### Problem

When an API token is configured (`DAPR_API_TOKEN`), every request to the Dapr HTTP API must carry it in the `dapr-api-token` header, except `GET /v1.0/healthz` and `GET /v1.0/healthz/outbound`.
The exemption compared the decoded request path with these routes, while the router matches the escaped path.
A request such as `GET /v1.0/healt%68z` or `GET /v1.0%2Fhealthz` decoded to `/v1.0/healthz` and skipped the token check, but matched no route.
Unmatched requests are handled by service invocation, so the request was invoked without a token.

### Impact

You were affected if you configured an API token and untrusted clients can reach the Dapr HTTP API port.
In Kubernetes the injector binds the API to the loopback interface by default, so only processes in the same pod could reach it unless `dapr.io/sidecar-listen-addresses` was changed.
In self-hosted mode the API listens on all interfaces by default.

A client without the token could make the sidecar send a `GET` request to the target named in the `dapr-app-id` header: the local app, any app in the mesh, an HTTPEndpoint resource, or any `http://` or `https://` URL the sidecar can reach (server-side request forgery).
The method was always `v1.0/healthz`, but the query string, headers and body were passed through.
Calls to other apps were sent with the sidecar's own identity, so their access control policies treated them as calls from this app.

This is the same class of issue as the earlier [API token authentication bypass](https://github.com/dapr/dapr/security/advisories/GHSA-59m6-82qm-vqgj).

Reported by Lee SeongHyeon.

### Root Cause

The API token middleware checked whether a request was a health check by comparing the decoded `URL.Path`.
The router matches routes against the escaped path, so any request that percent-encoded a character of the health check path was exempt from the token but was not routed to the health check handler.

### Solution

The API token middleware now compares the same escaped path the router matches, so a percent-encoded health check path requires the API token.
`GET /v1.0/healthz` and `GET /v1.0/healthz/outbound` remain exempt.

## Security: Sidecars relayed proxied gRPC calls from other sidecars under their own identity

### Problem

Each sidecar listens on an internal gRPC port (`50002` by default) that other sidecars use for service invocation, including gRPC proxying.
When a gRPC proxy call arrived on that port addressed to a different app (in the `dapr-callee-app-id` or `dapr-app-id` metadata), the sidecar forwarded it to that app's sidecar.
It set itself as the caller (`dapr-caller-app-id` and `dapr-caller-namespace`) and connected with its own mTLS identity.
The sidecar also treated an app with its own app ID in another namespace as the local app.

### Impact

Any workload with a Dapr identity, in any namespace, could relay a gRPC call through another app's sidecar.
For example, a workload could send a call to app B's internal port addressed to app C.
App C's sidecar then evaluated its access control policy against app B, not the real caller, and app C received `dapr-caller-app-id: B`.
This bypassed service invocation access control policies, and any caller checks in application code, whenever some other app in the mesh was allowed to call the target.

Reported by Lee SeongHyeon.

### Root Cause

The same gRPC proxy handler serves both the API port, which receives calls from the local app, and the internal port, which receives calls from other sidecars.
Only the path that delivers a call to the local app distinguished between the two.
The path that forwards a call to another app ran for calls from other sidecars as well.
The check for the local app compared the app ID but not the namespace.

### Solution

On the internal port, the gRPC proxy now only serves calls addressed to the local app, and returns `PermissionDenied` for any other target.
Sidecars never send such calls themselves, so service invocation between apps is unchanged.
The local app check now compares both app ID and namespace, so a call addressed to `myapp.other-namespace` is no longer delivered to `myapp` in the current namespace.

## Security: Scheduler prefix delete removed other apps' jobs

### Problem

The Scheduler `DeleteByMetadata` API with `id_prefix_match` set and a job target deleted every job whose key started with `app||<namespace>||<app ID>`, without a delimiter after the app ID.
This also deleted the jobs of every other app in the same namespace whose app ID starts with the caller's app ID.
For example, a request from `orders` also deleted the jobs of `orders2` and `orders-payments`.

### Impact

Any workload with a Dapr identity for an app in a namespace could call the Scheduler directly and delete the jobs (Jobs API) of other apps in that namespace whose app ID starts with its own.
Jobs could not be read this way, and other namespaces were not affected.
Dapr sidecars only send `id_prefix_match` for actor reminders, so applications did not trigger this themselves.

### Root Cause

The Scheduler authorizes the request against the caller's namespace and app ID, then builds an etcd key prefix from them.
For job targets, the delimiter after the app ID was left out when prefix matching was requested, so the prefix matched longer app IDs too.
The actor reminder path already always delimits the actor type for the same reason.

### Solution

The Scheduler now always ends the key prefix for job targets with the delimiter, so `id_prefix_match` only applies to actor reminder IDs, as the API documents.
A prefix delete for a job target now deletes only the jobs of the calling app.

## Security: Public port accepted unauthenticated, unbounded metadata writes

### Problem

The sidecar's public HTTP port (`--dapr-public-port`, `3501` in Kubernetes) serves the health checks used by Kubernetes probes and the metadata API.
Besides `GET /v1.0/metadata`, it also served `PUT /v1.0/metadata/{key}`, which stores a value in the sidecar's extended metadata.
The public port does not use the API token, and it did not apply the request body size limit, so this endpoint read request bodies of any size and kept every key in memory.

### Impact

In Kubernetes the injector always enables the public port and binds it to all interfaces of the pod.
Any client that could reach the pod could, without a token, send large or many `PUT /v1.0/metadata/{key}` requests and exhaust the sidecar's memory, restarting or killing it.
It could also add arbitrary entries to the extended metadata returned by `GET /v1.0/metadata`.

### Root Cause

The public port was given the same metadata endpoints as the main API port, including the write endpoint, but none of the main port's API token or body size middleware.
The extended metadata store has no limit on entry count or size.

### Solution

The public port now only serves read-only (`GET`) endpoints: `GET /v1.0/metadata`, `GET /v1.0/healthz` and `GET /v1.0/healthz/outbound`.
`PUT /v1.0/metadata/{key}` remains available on the main API port, which applies the API token and the body size limit.

**Breaking change:** `PUT /v1.0/metadata/{key}` on the public port now returns `404`. Clients must send it to the Dapr HTTP API port instead.

## Security: Sentry OIDC discovery document poisonable via `X-Forwarded-Host` with an allowed hosts list

### Problem

When Sentry runs its OIDC server without a static JWT issuer (`--jwt-issuer`) or JWKS URI (`--oidc-jwks-uri`), it builds the `issuer` and `jwks_uri` fields of `/.well-known/openid-configuration` from the request host.
With an allowed hosts list (`--oidc-allowed-hosts`), it uses the `X-Forwarded-Host` header for this once the header has passed the allowed hosts check.
That check split the header into host and port without validating the port, so `X-Forwarded-Host: sentry.example.com:80@attacker.example` passed as host `sentry.example.com`.
The discovery document was then built from the raw header, with `issuer` set to `https://sentry.example.com:80@attacker.example` and `jwks_uri` set to `https://sentry.example.com:80@attacker.example/jwks.json`, which both point to `attacker.example`.
The response was sent with `Cache-Control: public, max-age=3600`.

This completes the fix for "Security: Sentry OIDC discovery document poisonable via `X-Forwarded-Host` (CWE-346)" in Dapr 1.17.8, which made an allowed hosts list the precondition for `X-Forwarded-Host` to be used.

### Impact

You were affected if Sentry's OIDC server is enabled with `--oidc-allowed-hosts` set to specific hosts (not `*`), and neither `--jwt-issuer` nor `--oidc-jwks-uri` is set.
This is the configuration the Dapr 1.17.8 release notes recommend for reverse proxy deployments.
The default Helm values leave the allowed hosts list empty, and Sentry then ignores `X-Forwarded-Host`, so default installations were not affected.

An attacker able to send requests to the OIDC endpoint, directly or through a proxy that passes `X-Forwarded-Host`, could get a discovery document whose `jwks_uri` points to a server they control.
A relying party that fetched that document, or received it from a shared cache, could trust the attacker's signing keys and accept forged JWTs for Dapr workload identities.

### Root Cause

The allowed hosts check compared the header value with the list, and otherwise compared the host part returned by `net.SplitHostPort`, which accepts any text as the port.
The discovery handler did not use the validated host part. It parsed the raw header value as a URL, and the text before `@` became URL user info.

### Solution

Sentry now parses the host value (`X-Forwarded-Host`, or the `Host` header) once.
The value must be a host with an optional numeric port, with no user info, path, query or fragment, and its host or host and port must be in the allowed hosts list. Otherwise Sentry returns `403`.
The discovery document is built from that validated value.
A discovery document built from the request host is now sent with `Cache-Control: no-store`.
It is still sent with `Cache-Control: public, max-age=3600` when both the issuer and the JWKS URI are configured statically.

## Security: Malformed encrypted state values crashed the sidecar

### Problem

For a state store with automatic encryption (`primaryEncryptionKey`), Dapr decrypts every value it reads.
A stored value made Dapr panic during decryption if any of the following was true:

- It did not end with the `||<key name>` suffix that Dapr appends on write.
- Its key name matched neither the primary nor the secondary key.
- Its ciphertext was shorter than the nonce.

Over the gRPC API (`GetState` and `GetBulkState`) the panic crashed the sidecar. Over the HTTP API the request failed.

### Impact

Anyone who could write to the same state store data without going through the encrypted component could crash the app's sidecar each time the app read that key over gRPC.
This includes another app or another component on the same database, table or key prefix.
The same crash happened without an attacker when a store already held unencrypted values before encryption was enabled, or held values encrypted with a key that was later removed from the component.

### Root Cause

The decryption code took the key name from after the last `||` without checking that the separator was present.
It used an empty key when the name matched no configured key, and split the decoded value at the nonce size without checking its length.
The gRPC API server does not recover from panics.

### Solution

Dapr now returns an error for these values instead of panicking: gRPC `Internal` or HTTP `500`, with the existing state store error code.
Other keys and valid encrypted values are not affected.

## Security: Outbox processed forged messages from its internal topic

### Problem

With the transactional outbox enabled on a state store, Dapr publishes each outbox event to an internal topic first and subscribes to that topic itself.
When it received a message there, it looked up the state key named by the message's `id`, republished the whole message to the outbox business topic, and then deleted that state key.
It accepted any `id`, not only the outbox marker keys it creates (`outbox-<uuid>`).
A message without a `datacontenttype` field made Dapr panic.

### Impact

The internal topic name is predictable (`<namespace><app ID><topic>outbox`).
Any client that could publish to the same pub/sub broker could send a message to it, for example another app using the same pub/sub component with `rawPayload` when no topic scopes restrict it.
With an `id` naming an existing key in the outbox state store, including another app's key such as `otherapp||customer-42`, the attacker could:

- Have their own message published to the business topic as an outbox event of the target app.
- Delete that state key.
- Crash the sidecar, if the message had no `datacontenttype`.

### Root Cause

The outbox subscriber trusted the `id` and the rest of the message from the broker, and used the `id` directly as a state key.
It also read `datacontenttype` with an unchecked type assertion.

### Solution

The outbox subscriber now drops any message whose `id` is not an outbox marker key (`outbox-<uuid>`), before it reads or deletes state, and logs a warning.
A message without `datacontenttype` is published with the default content type instead of crashing the sidecar.

## Security: gRPC servers accepted request headers far beyond the configured read buffer size

### Problem

The `--read-buffer-size` option (annotation `dapr.io/read-buffer-size`, default `4Ki`) sets the maximum request header size for the Dapr HTTP and gRPC servers.
The gRPC API server and the internal gRPC server that other sidecars call multiplied the value by 1024 a second time, so with the default they accepted 4 MiB of request headers instead of 4 KiB.
In addition, the API token was compared with ordinary string comparison rather than a constant-time comparison.

### Impact

A client that could reach the gRPC API port, or a sidecar calling the internal port, could make the sidecar hold up to 4 MiB of headers per request, a thousand times the configured limit.
This raised the memory a client could make the sidecar use.
The non-constant-time token comparison could in theory leak timing information about the API token. No practical attack is known.

### Root Cause

The read buffer size was once configured in KiB and is now stored in bytes.
The HTTP servers use the value in bytes, but the gRPC servers still converted it from KiB.

### Solution

The gRPC API server and the internal gRPC server now limit request headers to `--read-buffer-size` bytes, with a minimum of 64 KiB.
The minimum is above Envoy's default limit of 60 KiB, so gRPC metadata that passes such a proxy is still accepted.
The HTTP and gRPC API token checks now use a constant-time comparison.

**Breaking change:** gRPC calls to the Dapr API, including gRPC proxying, whose metadata exceeds 64 KiB, or `--read-buffer-size` if that is larger, now fail with gRPC `Internal` ("header list size ... violates the maximum size").
Before, metadata of up to 4 MiB was accepted with the default settings.
If your app sends more than 64 KiB of gRPC metadata, raise `--read-buffer-size` or the `dapr.io/read-buffer-size` annotation.

## Security: Service invocation access control ignored HTTP verb rules for requests without metadata

### Problem

Service invocation access control policies can allow or deny an operation per HTTP verb (`httpVerb`).
When a sidecar received a service invocation request from another sidecar, it only read the HTTP verb for the access control check if the request carried metadata.
A request without metadata was checked without a verb, so the app's default action applied instead of the verb rule.
The request was still sent to the app with the HTTP verb it specified.

### Impact

You were affected if you used access control policies with `httpVerb` rules that deny some verbs of an operation while the app's default action is `allow`, and the target application uses the HTTP app protocol.
Sidecars always send metadata, so normal service invocation was not affected.
An attacker with any Dapr identity that the policy covers could call the target sidecar's internal port directly, without metadata.
That way they could invoke a denied verb, for example `DELETE /admin` when only `GET` is allowed.

### Root Cause

The access control check took the HTTP verb from the request's HTTP extension only when the request metadata was non-empty.
The metadata is set by the calling sidecar, so a crafted request could leave it empty.

### Solution

For HTTP apps, the access control check now always uses the HTTP verb from the request, the same verb that is sent to the app.
