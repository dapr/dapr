# Dapr 1.19.1

This update contains the following bug fixes:
- [Sidecar leaked connections while the Placement service was unreachable](#sidecar-leaked-connections-while-the-placement-service-was-unreachable)
- [Security: Fixes go-jose denial of service - CVE-2026-116587, CVE-2026-116586](#security-go-jose-denial-of-service)

## Sidecar leaked connections while the Placement service was unreachable

### Problem

While the sidecar could not reach the Placement service, it tried to connect about twice a second. Each attempt opened a new gRPC connection, and the sidecar did not close it when the attempt failed. Each leaked connection kept trying to reach Placement, with its own goroutines, until the sidecar restarted.
The sidecar also did not close the connection when a stream to Placement ended.

### Impact

You were affected if a sidecar could not reach the Placement service for a sustained period, for example while its pods restarted or crash looped. The goroutine count and memory use of every sidecar that connects to Placement grew for as long as the outage lasted. In a test with Placement stopped, the goroutine count of the sidecar grew by about 8 every second. Restarting the sidecar released the connections.

### Root Cause

The sidecar dials a connection to a Placement host and then opens the Placement stream on it. The dial does not wait for the host, so it succeeds while Placement is down, and only opening the stream fails.
When opening the stream failed, the sidecar returned the error without closing the connection, and the retry loop dialed another one. When a stream ended, the sidecar cancelled the stream but did not close its connection.

### Solution

The sidecar closes the connection when opening the stream fails, and closes it when the stream ends.

## Security: go-jose denial of service

### Problem

An upstream dependency of Dapr, `github.com/go-jose/go-jose/v4`, had three vulnerabilities in v4.1.4:

- [CVE-2026-116587](https://github.com/go-jose/go-jose/security/advisories/GHSA-mgcc-cww5-fp2q) (high): denial of service when go-jose parses a JWK that contains an RSA key.
- [CVE-2026-116586](https://github.com/go-jose/go-jose/security/advisories/GHSA-vvm8-gf78-28g4) (medium): a crash during JSON parsing.
- [CVE-2026-116585](https://github.com/go-jose/go-jose/security/advisories/GHSA-4w3g-jfj2-cw2q) (medium): a panic during CBC-HMAC processing.

### Impact

Dapr calls go-jose only through `go-spiffe`. It parses the JWKS in the trust bundle when the trust anchors load, and it parses the JWT that Sentry issues to the sidecar. These inputs come from the Dapr control plane, not from application requests.

CVE-2026-116587 and CVE-2026-116586 are on these paths in daprd and in each control plane service. Both are denial of service. CVE-2026-116585 is in JWE decryption, which Dapr does not use.

### Root Cause

Dapr pinned go-jose at v4.1.4. go-jose v4.1.5 fixes CVE-2026-116586 and CVE-2026-116585, and v4.1.6 fixes CVE-2026-116587.

### Solution

This release upgrades `github.com/go-jose/go-jose/v4` from v4.1.4 to v4.1.6.

go-jose v4.1.6 rejects an RSA key with a modulus larger than 4096 bits in a JWK. This affects you only if both of these conditions are true:

- JWT issuing is on in Sentry.
- You supply your own RSA JWT signing key that is larger than 4096 bits.

In that case, daprd and the control plane services cannot load the trust bundle, and they stop with the error `failed to parse JWT bundle`. Before you upgrade, replace the key with an RSA key of 4096 bits or fewer, or with an EC key. The JWT signing key that Sentry generates is RSA-2048, and it is not affected.
