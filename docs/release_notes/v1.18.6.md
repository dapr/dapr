# Dapr 1.18.6

This update contains the following security fix:
- [Security: Service invocation delivered spoofed caller identity headers to the target app](#security-service-invocation-delivered-spoofed-caller-identity-headers-to-the-target-app)
- [Security: Scheduler accepted actor reminders targeting another app's internal workflow actors](#security-scheduler-accepted-actor-reminders-targeting-another-apps-internal-workflow-actors)

## Security: Service invocation delivered spoofed caller identity headers to the target app

### Problem

On service invocation, Dapr tells the target app who called it through the `dapr-caller-app-id`, `dapr-caller-namespace` and `dapr-callee-app-id` headers (gRPC metadata for gRPC apps).
A calling app could send its own values for these headers, and they reached the target app alongside the values Dapr set:

```text
Dapr-Caller-App-Id: admin
Dapr-Caller-App-Id: checkout
```

- Service invocation through the HTTP API: a header such as `Dapr-Caller-App-Id: admin`, in any casing, reached the target app as a second value of the header, in random order.
- gRPC proxying: the calling app's `dapr-caller-app-id` value always came before the real one, and Dapr never set `dapr-caller-namespace`, so the target app received only the namespace the calling app sent.

### Impact

You were affected if a target app makes authorisation or tenancy decisions from these headers and uses the first value it finds (as Go's `http.Header.Get` and `metadata.Get(...)[0]` in gRPC do).
Any app able to invoke the target app could then make it believe the call came from a different app or namespace.

Dapr's own access control policies, workflow access policies and metrics were not affected: they use the calling sidecar's mTLS identity, not these headers.

### Root Cause

The HTTP API copies every request header into the invocation metadata and keeps the casing Go gives it, so `dapr-caller-app-id` sent by an app is stored as `Dapr-Caller-App-Id`.
The calling sidecar then set the identity headers under their lowercase names without removing other casings, so both keys travelled to the target sidecar, which merged them into one header with two values when delivering the request to the app.
Self-invocation already removed these headers in any casing, but cross-app invocation did not.

On the gRPC proxy path, the calling sidecar forwarded the app's metadata and appended its own identity values instead of replacing them, and never set `dapr-caller-namespace`.
The target sidecar passed all of these values to the app without checking them.

### Solution

- The calling sidecar now removes these headers in any casing before setting them, on every service invocation path.
- On the gRPC proxy path, the calling sidecar replaces the identity metadata instead of appending to it, and now also sets `dapr-caller-namespace`.
- The target sidecar now sets these headers itself before delivering the request, so apps are protected even while calling sidecars still run an older version. This covers service invocation and actor invocation received from another sidecar. With mTLS enabled, `dapr-caller-app-id` and `dapr-caller-namespace` come from the calling sidecar's mTLS certificate (SPIFFE ID) and, for service invocation, `dapr-callee-app-id` is the target's own app ID. With mTLS disabled, the target sidecar keeps the single value set by the calling sidecar and drops the rest.
- Caller identity headers in actor and workflow metadata received from the user-facing APIs are now removed in any casing.
- gRPC proxied self-invocation (an app invoking its own app ID) now carries the identity headers set by the sidecar, with caller and callee both the app itself, as HTTP self-invocation already did.

This is a behaviour change: with mTLS enabled, the caller identity headers an app receives are now always set by its own sidecar from the caller's mTLS identity, and gRPC proxied calls now carry `dapr-caller-namespace`.
With mTLS disabled there is no verified identity to fall back on: if the calling sidecar has not been upgraded, `dapr-caller-namespace` on gRPC proxied calls still reflects the value the calling app sent, so upgrade every sidecar to close the gap fully.

## Security: Scheduler accepted actor reminders targeting another app's internal workflow actors

### Problem

The Scheduler authorized actor reminder job requests only by checking that the job metadata namespace and app ID matched the caller's mTLS (SPIFFE) identity.
The actor type the reminder targets was not checked against the caller.
An application with a valid Dapr identity in a namespace could therefore schedule, read, list or delete reminder jobs on the reserved internal actor types of any other application in that namespace (`dapr.internal.<namespace>.<appid>.workflow`, `.activity` and so on).

### Impact

A compromised or malicious application in the same namespace could:

- Trigger reminders on another application's workflow and activity actors.
  The Scheduler delivers the reminder to the sidecar hosting that actor type, which executes it locally.
  The per-operation workflow access policy checks guarding the sidecar-to-sidecar reminder RPC do not apply to reminders delivered by the Scheduler.
- Run an arbitrary activity registered by the target application with attacker supplied input, by scheduling the activity execution reminder on the target application's `.activity` actor type.
- Inject a `TimerFired` event, or an activity result (`TaskCompleted` or `TaskFailed` with attacker supplied payload) into a workflow instance of the target application.
  Injected activity results are accepted only when they match a task the workflow is waiting on, and workflow history signing, when enabled, rejects unsigned results.
- Forge the result of an activity the target workflow is waiting on, by scheduling an `activity-result-*` reminder on the target application's `.workflow` actor type carrying a `TaskCompleted` or `TaskFailed` event for the outstanding task.
  The workflow actor accepted the result as if it came from the application the activity was dispatched to, so the workflow continued with attacker supplied output, or failed, while the real activity result was later discarded as a duplicate.
- Delete another application's workflow reminders, stalling its workflows.
- Delete every reminder job on every internal actor type in the namespace at once, by requesting a bulk delete by metadata with an ID prefix match on the user actor type `dapr`, whose key is a prefix of every `dapr.internal.<namespace>.<appid>.*` key.
- Schedule an `activity-result-*` reminder on another application's workflow actor carrying an event that is not an activity result.
  A raised event or a termination was admitted to the workflow inbox without any creator check.
  A `TimerFired` event crashed the sidecar hosting the workflow actor, since the inbox save cannot hold a timer event and the reminder goroutine does not recover from the panic.

The attacker needs a valid Dapr identity in the same namespace as the target application, so the issue does not cross namespace boundaries and does not affect deployments without mTLS beyond what an unauthenticated Scheduler already allows.

### Root Cause

The Scheduler's job authorization ignored the actor type of actor targeted jobs.
Only the placement service and the Scheduler's embedded placement checked that an application does not claim another application's `dapr.internal.<namespace>.<appid>.*` actor types, and that check applies to hosting actor types, not to scheduling reminders on them.

### Solution

The Scheduler now rejects with `PermissionDenied` any actor targeted job request (schedule, get, delete, list, delete by metadata and delete by name prefix) whose actor type is a reserved internal type `dapr.internal.<namespace>.<appid>.*` that does not belong to the requesting application and namespace.
User actor types are not restricted, so applications can still create reminders on actors hosted by other applications.
Activity result reminders (`activity-result-*`) on another application's workflow actor type in the same namespace remain allowed, since an activity host uses them to return a result to the workflow's application when the workflow's sidecar is unreachable.
That exception applies only to scheduling the job without overwrite: reading, deleting or replacing such a job on another application's workflow actor is denied, and the activity host creates these reminders without overwrite, treating an already existing job of the same name as a successful create.
Delivery of such a result is still subject to the workflow's own admission checks (the result must match an outstanding task of the current execution) and to workflow history signing when enabled.
The Scheduler also always terminates the actor type with the key delimiter when it builds a key prefix from job metadata, so an ID prefix match can only match actor IDs of that exact actor type and a bulk delete can no longer cross from one actor type into another.

The workflow actor now also verifies who created an activity result reminder.
The Scheduler verifies the creating application's identity when the reminder job is scheduled and sends it back to the sidecar when the reminder fires, and the sidecar passes it to the workflow actor.
An activity result reminder whose creator is neither the application the activity was dispatched to nor the workflow's own application is dropped and acknowledged, so the one-shot reminder is deleted rather than retried, and the workflow keeps waiting for the real result.
Reminders without a known creator (reminders stored in the actor state store, or delivered by a Scheduler from an older release that does not send the job metadata back) are accepted as before.

The workflow actor now drops, and acknowledges so that the reminder is deleted, any `activity-result-*` reminder whose payload is not a `TaskCompleted` or `TaskFailed` event, whoever created it, so no other event type can enter the inbox through that name and a `TimerFired` payload no longer crashes the sidecar.

An activity result created by another application for a task the workflow has not scheduled yet is no longer parked in the inbox, where it would have been consumed without a creator check once the task was scheduled.
The workflow actor refuses it as not yet durable, so the reminder is retried while the scheduling may still be committing, is checked against the dispatch target once the task is scheduled, and is dropped after the retry window otherwise.

The creating application is now carried when a sidecar that received a fired reminder forwards it to the replica of the same application that hosts the actor.
The receiving sidecar trusts the forwarded creator only from a replica of its own application, as identified by the peer's mTLS identity, and otherwise records the peer application itself as the creator, so a forged reminder cannot shed its creator by being forwarded.
